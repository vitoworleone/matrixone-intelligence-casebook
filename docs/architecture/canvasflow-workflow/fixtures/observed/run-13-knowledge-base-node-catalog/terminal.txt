你:把公司的产品手册做成知识库，以后能按意思搜到相关段落
…模型在推

我按最常见的情况画：手册是带文字层的 PDF 或 Word，直接从里面提文本。要是你手上其实是扫描件或纸质版，第一步会换成 OCR，这个问题我列在下面了。另外这条链只把现有手册建成知识库，没有加“手册改版后自动更新”这一步——如果手册会改版，需要再补一条重新处理的路径，你要的话我再加。

方案 v1 · partial · 5 步 · 2 项待确认
目标:把公司产品手册建成知识库，支持按语义（按意思）检索并返回相关段落。
理解
  u1  「把公司的产品手册做成知识库」→ 把现有的产品手册（文档）处理成一个可检索的知识库。
  u2  「以后能按意思搜到相关段落」→ 检索方式是语义检索（按意思匹配，不是关键词），返回的粒度是段落。
路线
  s1  提取正文文本
      进:带文本层的产品手册（PDF 或 Word 文档）
      出:保留标题层级的纯文本正文
  s2  按段落切分
      进:保留标题层级的纯文本正文
      出:带来源定位的段落文本块
  s3  段落向量化
      进:带来源定位的段落文本块
      出:每个段落对应的语义向量
  s4  建成可检索知识库
      进:段落文本块及其语义向量
      出:语义可检索的知识库索引
  s5  按意思检索返回段落
      进:用户的自然语言查询（外部输入）
      出:命中的相关段落（附来源定位）
待确认
  q1  产品手册现在是什么形态？
      为什么:决定第一步是直接提取文本，还是要先做 OCR 扫描识别。
      备选:带文本层的 PDF / Word 文档 / 扫描件（无文字层） / 纸质手册 / 网页/HTML
  q2  搜索结果里说的“段落”按什么粒度算？
      为什么:决定切分那一步把正文切成多大的块，粒度不同召回效果差别很大。
      备选:自然段落 / 小节（带小标题） / 页面

你:扫描件和电子版混在一起，得先分开走。表格里的参数要能搜到，图片不重要。
…模型在推

扫描件和电子版分开走这点我并进去了：先按形态分流，扫描件走 OCR，电子版直接提文本，两路都要求把表格转成结构化文本、图片直接丢，然后在切分前汇合。表格这块我先按“整张表/按行作为可搜到的块”处理，保证参数能进检索；要是你要的是查到后只返回那一个参数而不是整张表，那属于切分粒度，回头可以调。段落粒度你还没说，我暂时还是按自然段落画，问题挂在下面。
