# 观察

真模型跑出来的行为记录。few-shot 例子照着这里的真实失误写，不凭想象写。
原始输出在 fixtures/observed/。目前的观察都来自 deepseek-v4-pro。

## 2026-09-02 首轮,三个场景

场景:合同 PDF(非结构化)、"帮我搞个工作流"(没闭环)、ODS→DWD→DWS(结构化数仓)。

成立的:

- 两条分支都对。描述清楚的出 partial 骨架;没闭环的不调工具、只说话,
  反问的正是两个地基(手上什么形态、最后要变成什么)。
- 必问的判据落地了。四个问题全是"错了看不出来"那类:扫描件还是文本层、
  "新增"口径、抽哪几个字段、写哪张表。没有塞校验、监控、去重这类步骤。
- 数仓场景的 u3 明确写"给报表用是消费端,不构成一次形态转变"——推导纪律
  被执行,而且被说了出来。
- 同题重跑结构稳定:合同场景跑两次,步骤、问题、编号完全一致。

失分寸的(few-shot 的靶子):

1. 提交轮零说话。三次提交没有一次先说话。只说话的轮次话说得很好,所以
   不是不会说,是调工具时不说。取舍已定(2026-09-02):损失小——透明的
   主承担者是方案本身(回读+缺口),说话是增益通道;提示词已从"先说一段话
   再提交"软化为"有方案里没格子放的判断就先说,没有不硬说";few-shot 里
   自然示范,不设闸不硬凑。
2. 【撤销一半,2026-09-02】步骤编号风格(s1 还是 ods_to_dwd)是语义中性的
   风格差异,不立规矩。真正要观察的是修订轮的编号稳定性——当天补测,见下。
3. 【裁决:不是问题,2026-09-02】一条 openQuestion 里带两问无妨。架构里
   没有逐条销账:用户的回答只是新上下文,模型整份重推,问题清没清看下一份
   方案里它还在不在,不需要一问一答对齐。(当时裁定)

已裁决的:

- 触发要不要独立成步——不构成问题。触发不转变任何数据形态,不在设计者管的
  语义层;到点了、来了个事件,都归执行者配置开始节点时处理。方案里带到
  "每天凌晨"这个事实即可,写在第一环说明里或单独占一步,设计层等价,
  不立规矩,fixture 也不改。(2026-09-02,当时裁定)

## 2026-09-02 修订轮

接着合同场景,替用户补一句:"PDF 都是扫描件。「新增」按文件落库时间算,
每天处理昨天落库的。"带上第一轮完整对话记录重调。原始输出:
fixtures/observed/run4-修订轮/turn-2.plan.json。

- 编号全部稳住。s1-s4 沿用;s2 原地改(标题、intent、input 换成 OCR 口径,
  编号不动)——界面上正确显示为"原地改"。s3、s4 一字未动。没被回答的
  q3、q4 保留原编号,没有重新排号。
- 扫描件信息让 s2 长出 OCR,且没有多拆一步——图像到文本仍是一次形态转变,
  原地改而不是插新步,切分纪律稳。
- 被回答的 q1、q2 消失;u5、u6 新增,承接补充的两句原话;readiness 保持
  partial(还剩字段和落表两问)。
- 重查是真的重查:u2 的 reading 里原有的"口径还需明确"尾巴被删掉了,
  不是机械保留旧文本。
- 这轮没说话——所有变化都落进了方案,按"有话则说"的取舍,合规。

## 2026-09-02 问了还说不清就先猜

裁决(当时裁定):数据源这类先问;用户答不上来,就按最常见的一种先画,问题留在
待确认里,提交之前说明按哪种画的。来源是对照另一份独立设计的"猜了就画":取它
"猜的要看得见"这一半,不取它"先猜后问"那一半——猜的东西会往下传,猜错一个后面
一串重画。提示词 <什么必须问> 加了一段,英文版同步。执行者侧的假设标记、一键改、
没确认不许跑,挂账。

验证:合同场景第一轮照常出问题(这次把存放位置单独问成 q5,共五问);第二轮替用户
答"合同是别的部门给的,放在哪我也说不清,你先按常见的来吧。另外 PDF 都是扫描件"。
原始输出:fixtures/observed/run5-说不清就猜/。

- 先说了话再提交:"存放位置我按'一个共享文件夹/目录'来画——执行前这个位置得确认"。
  这是 <提交之前说话> 第一次在真模型上被用到:方案里没格子放"这是猜的",它就说了。
- 猜画进了 s1 的 input:"存放新增合同扫描件的共享文件夹/目录"。
- q5 没有消失,改写成"我按'一个共享文件夹/目录'画了存放位置,实际是哪里?"——问题
  留着,而且自带"这是猜的"标记。readiness 仍是 partial。
- 扫描件那句照旧:q1 消失,s2 原地改成 OCR,r5、r6 新增承接两句原话。编号全稳。
- 它把自己的猜也写进了回读 r5:"授权我先按常见方式画;我按'一个共享文件夹/目录'处理"。
  回读栏本来是给用户核对原话用的,它顺手把猜放了进去,用户核对时也看得见。不立规矩。

## 2026-09-02 备选项与多轮命令(run5、run6、run7)

契约加了 options 之后,用仓库里的多轮命令 `npm run plan:chat -- --save` 跑:同一对输入
(合同一句 + 扫描件补话)跑了两遍,另加一次首轮。原始输出在 fixtures/observed/run5-备选项/
和 run6-编号身份/,连完整对话记录一起;run7 没入库,只看首轮有没有重交。

成立的:

- options 用在了该用的地方。三次首轮,"扫描件还是带文字层"次次给了备选项,run6 还多给了
  "两种都有";抽哪几个字段、写哪张表三次都不给。私有事实不编选项,判据被执行了。
  "新增"口径两次给了备选项,一次(run7)又塞回问题文本里,这条还没稳。
- 说话有了真实的正面例子。run5 首轮提交前:"我把合同 PDF 先按带文字层来画,如果是扫描件,
  第二步前面得多一道 OCR,这条我留成了选项"——分叉先画一条,并且说了出来。run6 修订轮:
  "我没有单独加扫描件质量判断/图像预处理这一步……执行时发现需要再加"——按一种情况处理了,
  说明了没加什么。三次里两次说了话,首轮零说话的记录被打破。
- 多轮命令把修订轮的跑法放进了仓库。--save 存下完整对话记录,能看见以前看不见的东西:
  闸门打回和重交。

失分寸的:

1. 编号身份。run5 修订轮理解栏重排:用户补的两句被插成 r2、r3,原来的 r2、r3 挤成 r4、r5,
   同一个编号换了内容,界面上会演成一行原地变形成另一句话。提示词补了一句"编号是身份不是
   位置,新条目用没用过的编号,砍掉的编号不复用";run6 同样两轮编号全部稳住:r1-r3 沿用,
   r4、r5 新增,s1-s3 原地改,s4 沿用,q1、q2 消失。一次坏一次好,不算证明,记录在案。
   这是 few-shot 的第一个真靶子:之前挂账说没有失败就不写例子,现在有了。
2. 顶层 description 被当成字段。run5、run6 首轮第一次提交都多了一个 description 字段,被
   闸门打回,重交才过。原因是契约文件顶层的 description 跟着进了工具参数,模型把它当成要填
   的格子。工具定义里去掉它之后 run7 首轮一次过。闸门本来就兜住了这一条,改的只是省一次往返。
   顺带发现命令行把第一次说的话丢了:重交那条回复不说话,只取最后一条就丢了第一段。已改成
   攒着,测试守着。
3. 来源位置问不问,两次判断相反。run5 修订轮它自己说"文件从哪个文件夹取属于执行时的配置,
   不影响链路走向,先不问";run6 首轮把它列成 q5 必问。按我们的判据,来源填错执行者搭不出
   读取节点,是骨架上的空格,不是静默错误,run5 的判断更对。不改提示词,先攒观察。
4. 切分跨运行不稳。三次首轮理解栏分别切成 4、3、3 段,步骤 4、4、3 步,语义上都说得通。
   编号稳定只在同一次对话的修订轮之间有意义,跨运行不比。

## 2026-09-02 提示词改成"只写模型眼前有的东西"之后(run8)

当时定了两条写提示词的尺子:不写禁令,写后果,让规则从后果里长出来;提示词里出现的
每样东西模型都得能在自己眼前找到——对话记录、schema、它上一轮交的那份、行业常识——
找不到的它只能猜,猜的就是默认路径。按这两条把"编号"和"备选项"两段重写:编号的理由
从"界面会原地变形"(模型没见过界面)改成"用户回话时拿编号指,编号一换内容,他指的和你
以为的就不是一句话";备选项的理由去掉"点一下省事"(界面),只留"你列的任何一项都是编的,
跟用默认值填上是同一回事"。同样两轮重跑,原始输出在 fixtures/observed/run8-原因版提示词/。

- 编号全稳:u1-u4 沿用(u2 原地改,把后来补的口径写进了 reading),u5、u6 新增,
  s1、s2 原地改,s3、s4 沿用,q1、q2 消失,q3、q4 沿用。
- 备选项:q1 三项(含"两者都有"),q2 四项口径;字段与表不给。跟前两次一致。
- 两轮都先说了话。首轮:"我按合同 PDF 自带文字层来画这条链,如果实际是扫描件……回一句
  就行",分叉先画一条并说出来;修订轮:"字段和写哪张表这两项还没给,其余都齐了"。
- 两轮零打回。来源位置没有列成问题,跟 run5 的判断一致。

到这里为止最干净的一次。跟 run6 相比,提示词少了"禁令味",行为没变差。一次不算证明,
记录在案。

## run10 执行者第一次真跑:run9 方案的 s1(2026-09-02)

拿 run9 那份合同方案(第二版)的 s1「筛出昨天落库的合同 PDF」,画布空的,没批注,单独跑一步,不接状态机。
DeepSeek,英文提示词,三个工具。8 个回合,4 分 41 秒,整段对话 22 条,原样在
`fixtures/observed/run10-执行者-s1/`(messages.json 整段对话、submission.json 它交的原样、
patch.json 换成状态机认的、context.json 桌上的五样、trace.txt 每个动作)。

它做了什么,按回合:第 1 回合一口气三个动作,搜 "list files directory disk"、查 Schedule Trigger、查
Read/Write Files(回的是菜单);第 2 回合带上 read 再查一次;第 3 到 5 回合连搜六次——"watch filesystem
new file"、"file trigger directory"、"list files folder metadata"、"read directory file list"、
"file stat metadata modified time"、"filter files by date"——都是在找一个能拿到文件落库时间的办法,
候选里没有一个是;第 6、7 回合查了 Code 和 Edit Fields 的参数,两个都没用;第 8 回合交:两个节点,
「每天定时触发」(每天 0 点,默认值它明写了出来)和「读取昨天落库的合同 PDF」(read,fileSelector
留空并写进 blanks,options.fileExtension 填了 pdf),一条线。从头到尾一个字没说。

它用到的参数名全在目录里,查过:fileExtension 在 read 的 options 里,daysInterval、triggerAtHour、
triggerAtMinute 在 rule 里。没凭印象编参数。

读出来的东西(这段是我的读法,不是数据):这一步的意思是「按落库时间圈定昨天的」,交回来的节点读的是
目录里全部 PDF,没有筛。平台的读文件节点给不出修改时间,它搜了六次没找到,看了 Code 一眼没用,
然后把「昨天」这个要求悄悄放下了。卡片的名字还叫「读取昨天落库的合同 PDF」,名字许的比节点做的多。
提示词告诉它说的话没人看,它就真的没说。这是「执行者不说话」那条第一次碰到实案:用户看到的是一张
名字里有「昨天」、参数里没有「昨天」的卡片。

顺带看见的两处工具的毛病:搜 "list files directory disk" 回的候选里有 Anthropic、Item List Output
Parser,查词太松;查 Code 节点回了 8 格,jsCode 出现四次、pythonCode 两次,是不同版本和模式下的
同名格没有合并,对模型是噪音。

## run11 / run12 真执行者第一次在状态机里走完整条链(2026-09-03)

执行者插进状态机(`EXECUTOR_MODULE=src/executor/executor.mjs`),同一句合同的话、同一句补充,让设计者出新方案,按开始走完,再批注、再按开始。两次各自一个文件夹;`executor/` 下是每一步执行者自己的对话记录(`01-r1` 是第一遍的 r1,`05-r1` 是第二遍的);`terminal.txt` 是终端原样;`输入.txt` 是我喂进去的几行,手写的。

**成立的:**

- 四步全做完。run11:r1 三个节点(定时、读文件、一个代码节点按文件 mtime 圈昨天),r2 OCR,r3 抽取节点加一个模型子节点,r4 写 Postgres。7 个节点、6 条线、7 处空位:目录、Mistral 凭据、抽哪些字段(q3 没答)、DeepSeek 凭据、库凭据、表名、字段映射——全是只在用户那边的信息,没有一处是编的。回合数 4 / 2 / 3 / 3。run12 第一遍形状一样,回合 6 / 2 / 3 / 3。

- 旁白每张卡都有,两处把它的判断摆到了明面:代码节点「按文件的修改时间(即写入存储的落库时间)过滤」——run10 里它悄悄拿 mtime 顶落库时间,这回写在卡上;写库节点「schema 先按默认 public」。
- 没批注再按开始,四步全说已经有了,每步一回合、3 条消息,没再搜没再查(run11 第二遍)。

- 设计者这次把步骤编号成 r1–r4,不是以前几次的 s1–s4。契约允许任何字母开头,提示词也没规定字母。命令行的说明里写死了 `/note s1`,run11 脚本喂的也是 s1,被拒「方案里没有 s1 这一步」。编号字母要不要定死,待定。
- n8n 把「抽取用哪个模型」拆成一个单独的子节点挂上去,画布上多一条「DeepSeek 模型 → 抽取」,跟数据线长得一样。这是借的目录的毛病,不是我们的:自己定义节点时「过模型」是一张卡,一格选模型、正文是提示词,不另开框。

## run13 换到自己的节点表之后第一次跑(2026-09-03)

## 界面上跑通,和跑不通的那几次(2026-09-03 夜 → 09-04)

### 一句话:模型偶尔把工具调用当正文写出来,而我们对这个接口讲错了协议

先后两次停在这上面。Plan Agent 那次,正文里是 `<invoke name="propose_plan">{...}`;
执行者那次,正文里是 `submit_step({ "kind": "patch", ... })`。两次的表现都是
「说了话但没有 tool_calls」,于是上面那层认为它什么都没交。

根因不是模型质量,是协议。三条证据:

1. **这个接口原生是 Anthropic 的。** 直接打 `https://api.kimi.com/coding/v1/messages`,
   HTTP 200,回来的是 `{"id":"msg_...","type":"message","content":[{"type":"thinking",...,"signature":"..."}]}`
   ——标准 Anthropic Messages API 响应,带 thinking 块和签名。
2. **漏出来的那段是 Anthropic 的工具调用语法。** `<invoke name=...>` 不是 OpenAI 的形状,
   OpenAI 的工具调用是结构化 JSON,不会出现在正文里。
3. **走原生路径,同一份提示词同一个工具,5 次全干净。** 块结构是 `thinking + text + tool_use`,
   这才是它真正的输出形态。

所以链条是:模型原生吐三种块(thinking / text / tool_use),我们走的 `/chat/completions`
是这个接口上的一层翻译层,要把三种块压平成 `{content, tool_calls}`。翻译的前提是模型
真的吐了 `tool_use` 块;它偶尔不吐块、把调用当正文写,翻译层就没东西可翻,原样落进 content。
而它更容易这么干,恰恰因为被翻译过的那份对话(工具描述换了形状、工具结果从 `tool_result`
块变成 `role:"tool"` 消息)已经不在它的训练分布上。

受控条件下打了 8 次没复现出来,所以**不知道概率是多少**,只知道机制是这个。
顺带一个代价:thinking 块原生带签名、能回喂给下一轮保持推理连贯,经过翻译层这部分是丢的。

两处都先在末端补了(认出正文里的假调用 → 当没交 → 让它重来)。**这是打在错的一层上的补丁,
补一处漏一处。正确的修法是按这个接口的原生协议说话。** 代价是模型层要多一种协议插座,
`openai-compatible.mts` 开头那句「不引厂商 SDK,换模型只换地址、key、模型名」就不成立了。
这个没定。

### 一道闸门在两处调,可选参数把它调成了两道

「接在谁后面就要有线接过来」这条加成了 `checkResult` 的第四个可选参数,状态机传了,
执行者那处没传。于是执行者自己那关比状态机松:它自己过了,到状态机才被退,而那时候它
已经没有机会改。表现出来就是模型偶尔忘画一条线,整趟停。

架构 ④ 本来就写着「没过:原因原样退给执行者,它在同一个来回里改了再交」,而且执行者
代码里确实有这条路——漏的不是机制,是两处口径不一致。改成闸门收方案里那一步本身
(`{ref, dependsOn}`),要看的东西都在那个对象里,传不掉。

### 修完之后第一趟走完的真跑

一句「把一批 PDF 文档转成带元数据的向量,写入向量数据库,供后续检索使用」:
方案 5 步,画布 8 个节点 8 条线,`endedBy: finished`,`problems: []`,没有孤点。
s1 一次交回 4 个节点,连成一条带条件分岔的链,两个分支都接回了下游。

**但分支标反了**:`有文字层吗？` → true 走 OCR、false 直接去切分,语义是倒的。
闸门查不出来也不该查——这是判断,不是机器转不动。这类错只能靠人看见、靠批注改。
它正好说明「停了要能说话」这条通道为什么必须有。

### K3 的节奏(对比 DeepSeek V4)

K3 想 35 秒,然后 1 秒之内把整份方案写完。慢的是想,写得极快。
DeepSeek 那边是想 40 秒、写 5 秒。所以等待期那三十几秒是一个稳定的「正在理解需求」,
后面那一秒是一串快速落下的行。
