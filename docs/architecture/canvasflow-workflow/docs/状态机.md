## 当前新增：生成完成后的整图修订（2026-09-05）

下面的分步构建、批注后重走记录描述首次构建和仍保留的旧入口。浏览器节点内的新输入走 `revise()`，不回到该节点对应的 step state，也不从 S1 重走。

用户从 S3 发一句要求时，会话冻结当前完整计划、完整画布、发起节点与步骤、当前要求、已应用要求及有关记录，交给执行 Agent。Agent 审视所有计划步骤后提交必要差量，可以同时改 S3 与 S5。`inspectRevision` 将差量合入临时画布，检查契约、节点表、连线、步骤覆盖与依赖、环路和粗类型；通过后画布只加一个版本，计划保持原样。每步影响说明是模型判断，不是语义验证。

修订共用规划／构建的执行权，处理期间允许写草稿，下一条写操作须等完成或停止。会话保存 `processing → checking → applied / unchanged / needs_plan / failed / stopped` 记录。只有 `applied` 替换画布；`applied` 与 `unchanged` 的要求进入后续上下文。拒绝、失败、停止和过期提交都不替换画布。当前计划未构建完，或请求引用旧画布版本时，发送前直接拒绝。

刷新和事件重连从当前服务会话恢复画布及修订记录；不包含服务重启持久化。真实连续修订见 [run14](../fixtures/observed/run14-节点整图修订/README.md)，实现见 [workflow-session.mjs](https://github.com/Bai-009/canvas-first-workflow/blob/824397ed995dc7e1293a383bf3b90d1bc1cdf63e/src/state-machine/workflow-session.mts) 与 [workflow-revision.mjs](https://github.com/Bai-009/canvas-first-workflow/blob/824397ed995dc7e1293a383bf3b90d1bc1cdf63e/src/state-machine/workflow-revision.mts)。

以下保留初次构建机制的推导历史；其中“全局一致由重走保证”不是对节点内整图修订的约束，也不能理解为重走能证明业务语义正确。

状态机管的是：一份东西从用户的话走到画布，每一步谁在动、动完沉淀了什么。Plan 阶段的那一半做出来了（[src/plan/plan-session.mjs](https://github.com/Bai-009/canvas-first-workflow/blob/824397ed995dc7e1293a383bf3b90d1bc1cdf63e/src/plan/plan-session.mts)），执行阶段的那一半，状态机的部分也做出来了（[src/state-machine/workflow-session.mjs](https://github.com/Bai-009/canvas-first-workflow/blob/824397ed995dc7e1293a383bf3b90d1bc1cdf63e/src/state-machine/workflow-session.mts)，2026-09-02）：开始、停、批注、走步、画布、记录。执行者本身还没有，是一个插口。

## 一条总规则：回合制

任何时刻只有一方在动。用户发一句，模型跑，用户等；模型回来，轮到用户。用户敲定方案按开始，执行者跑，用户不动；用户想动，先按停。

停止是一个明确的动作——发送键变成停止键——不能从「用户又打了字」推断出来。手滑打的字会把正在跑的一轮作废，还逼模型去读一句垃圾。

回合制替掉了早先设计的乐观并发（requestId、基线检查、过期丢弃）。那套机器解决的麻烦是两方同时动；两方从不同时动，它就没有出场理由。

## Plan 阶段（已做）

持有三样：对话记录、过了闸门的每一份方案（最后一份是当前方案）、这一轮跑没跑着。

规则一条：**当前方案只在新的一份过了闸门时才换。** 只说话的一轮、被停掉的一轮、几次都没过闸的一轮，都不碰它。

一轮的四种收场，都回到用户：

- 只说话没提交：记录多了它这句，方案不动。
- 方案过闸：记录多了工具调用和回执；当前方案换新，版本加一，上一版留着给界面按编号算增量。
- 几次都没过闸：这轮的往返不进记录，只留用户那句，方案不动，报错。
- 用户按停：同上，不报错。

代码：`createPlanSession` 的 `say` / `stop` / `currentPlan` / `revision`；两版之间的差异由 `diffPlans` 按编号算（沿用、原地改、新增、消失）。测试守着「只在过闸时换」「跑着不收第二句」「停掉只留用户那句」「第二轮交给模型的记录带着第一轮的工具调用和回执」。多轮命令：`npm run plan:chat`。

## 执行阶段（状态机已做，执行者是插口）

先看一遍画面，再列规则。画面用 [run8](../fixtures/observed/run8-原因版提示词/turn-2.plan.json) 那份方案：四步，s1 圈昨天落库的 PDF，s2 OCR 出文本，s3 抽字段，s4 写表；q3 抽哪些字段、q4 写哪张表没答。画布空着。

### 画面

**第一遍。** 用户按开始。

- 做 s1。执行者桌上摆着五样：整份方案；一张条子写"现在做 s1"；画布（空）；这一步没答的问题（没有）；批注（没有）。它自己去平台上翻可用的节点，搭一个"按落库时间筛 PDF"，填上路径、时间范围昨天、类型 PDF。交回一份画布改动：加一个节点。状态机过画布闸门（节点类型存在、必填的格填了或标了待填、线接在存在的节点上），提交。画布上现在有一个节点，它出的是文件清单。这一步里翻平台、试参数攒下的消息，扔了。
- 做 s2。桌上换了一样：画布不空了，有 s1 的节点，还有它实际出的清单长什么样。搭 OCR 节点，输入接 s1 清单里的路径。交回，过闸，提交。
- 做 s3。桌上多了一样：q3 没答。字段那一格留空，标"待填"。闸门只查留空的格标没标。提交。
- 做 s4。同样，表名留空。
- 跑完，轮到用户。画布上四个节点、两个空格。

**批注。** 用户对着完整的工作流批注：在 s1 上写"PDF 太大，先拆成单页图片再往下送"。批完按开始。

**第二遍。** 状态机从 s1 重走。

- s1。桌上第 5 项有东西了：那句批注。重做，现在出的是单页图片清单。交回替换，提交。
- s2。桌上：s1 现在出的是单页图片；画布上 s2 那个节点接的是 PDF 路径。对不上，重做：按页 OCR，再把一份合同的页拼回一段文本。交回，提交。
- s3。桌上：s2 出的还是每份合同一段文本；画布上 s3 接的正是这个；没批注。交回一句"画布上已经有了"。状态机不动画布。
- s4。同样，已经有了。
- 跑完，轮到用户。状态机手里的记录：s1 重做、s2 重做、s3 跳过、s4 跳过。

整个过程里没人对执行者说过"检查整体顺不顺"。s2 被重做，是因为它桌上那两样对不上。

### 从画面里拆出来的规则（2026-09-02 认了）

1. **每一步交给执行者五样。** 整份方案；现在做哪一步；画布上已有什么，含前序节点的实际输出；挂在这一步上没答的问题；挂在这一步上的批注。平台上有什么节点，它自己拿工具查，状态机不替它查。方案里的理解栏已经装着用户说过的事实，所以不给对话记录：用户的话沉淀进方案，这正是"不长在对话框里"。
2. **前序结果从画布读，不靠攒消息带过去。** 一步之内攒消息（查节点、试参数、改一版），提交后扔，下一步从画布起头。攒消息跨步的两种翻车：用户改了上游节点，消息里记的还是老样子；方案改了要往回剪，剪到哪一步还得剪对。每步从画布起头就没有东西要剪，从头对账才便宜。
3. **执行者交回的是一份画布改动**：加或换哪些节点、怎么连、哪几格留空。状态机只过画布闸门然后提交，不判对错：闸门只拦机器缺了转不动的，这一步搭得对不对状态机看不出来，也不该看。看得出来的是用户，在画布上看。
4. **中途只能停。** 执行者的一轮是整个工作流，看着长出来的时候用户不动手，想动先按停（理由还是手滑那条）。批注在跑完之后，对着完整的工作流批。批注挂在步骤编号上而不是节点上，节点重建它还在，执行者每步开工时读到。
5. **批完一批按开始，从 s1 重走。** 每一步执行者看画布判断：已经有了就跳过，批了的或上游变了的重做。放弃"批一条跑一条"（Cursor Cmd+K 那种）：批的是 s1，s1 的输出变了，s2 接的还是老的，只动 s2 之外的东西看不见，s2 就悄悄错了。
6. **全局一致由重走保证，提示词里不写"检查整体顺不顺"。** 那句话要的是一种自觉，不是一样眼前的东西：模型要么翻到一半漏一个接口，要么回一句"已检查"，外面分不出来，目标从"把 s1 修好"变成"显得检查过了"。规模越大该抓的接口越藏。重走把它拆成每步看一个接口：这一步要什么、上游实际出什么、画布上这一步现在接的什么，一比就出。类比：改了函数签名，靠得住的是编译器走每个调用点，不是"保持其他地方一致"那句话。
7. **推论：提示词只有一种活，搭一步。** 提示词按活换，不按状态换；批注只是第 5 项，不另写一份修节点的提示词。s1 和 s2 用同一份提示词，差别只在桌上那五样的内容。

行业叫法：交回的画布改动叫 patch；只管流转不判对错的状态机叫 orchestrator；从头重走、每步判"已经有了"叫 reconcile / covered；状态放存储里不放对话里、每步从存储重建，Kubernetes 那类系统从头对账便宜也是这个原因。

### 代码里做成了什么

`createWorkflowSession` 把 Plan 会话原样包在里面，往下长一段。手里多攥三样：画布（节点、线、版本号）、批注、每次走步的记录。多三个动作：

- `start()`：按开始。按"接在谁后面"分波：互不依赖的步同一波一起交给执行者，一波做完才开下一波，同一波的步看到的都是这一波开始前的画布（2026-09-03）。每步拼一次上下文（`assembleTable`，就是上面那五样），喊一次执行者，收回的改动查过就换掉这一步原有的节点，版本加一，记一笔；"已经有了"就记一笔不动画布。走完拿方案对着整张画布查一遍形状：每一步有没有节点，接在谁后面的有没有线真的从那一步接过来。查出来的写进记录，先不自动发回。
- `stop()`：谁在跑停谁。停执行者，正在做的这一步作废，画布停在上次提交；执行者不理会停止信号、停了还交东西，一样不收。
- `annotate(step, text)`：只在轮到用户时能批，挂在步骤编号上。

执行者是插口：`async (拼好的上下文, { signal }) => 结果`。结果只认两种，`{ kind: "patch", nodes, edges }`（这一步的全部节点，整份重出）和 `{ kind: "covered" }`。状态机只查机器能查的：节点带名字、类型、参数、留空的格、是哪一步搭的；标的必须是这一轮做的那一步；名字不跟别的步撞；线接在存在的节点上、至少一头是自己的。节点类型在不在平台目录里、必填的格填没填，要等执行者那一段带着目录来。

线的归属这样定：进这一步的线由这一步自己在改动里声明，重做时老的进线全部换掉；出这一步的线是下游声明的，这头的节点名字还在（原地改）就留着，名字没了的连线一起去掉，下游重走时会看见自己没接上。

测试守着的：没方案不能开始；执行者位置空着不能开始；四步按顺序做完、版本每提交加一；互不依赖的步同一波做、拿到同一版画布；一个分岔的两条出口到同一个节点是两条线；固定答复插进来能走完整条链；每步的上下文里画布是做到这步时的样子、问题和批注挂对步；已经有了不动画布；跑着不收话、不收批注、不收第二次开始；停了画布停在上次提交、再开始从 s1 起；批注之后重走 s1 拿到批注、s2 看到新的 s1；上游重做下游却说已经有了，线断了会被查出来写进记录；执行者改了别的步的节点被拒、画布不动；执行者出错记下来换回用户；方案换版本后走的是新方案；Plan Agent 在跑时不能开始不能批注。

命令行：`npm run plan:chat` 里 `/start`、`/note r1 文字`、`/canvas`。执行者用 `EXECUTOR_MODULE=路径` 插；真的是 `src/executor/executor.mjs`（2026-09-03 起，run11 是它走的）；没插的时候 `/start` 明说做不了。`fixtures/doubles/fixed-executor.mjs` 是测试用的固定答复，交回的节点类型明写"固定答复(不是真节点)"，只为看状态机怎么动。

### 仔细想过后发现的洞（待确认，不急）

- **节点得记着自己是哪一步搭的。** 没这个，状态机不知道"画布上属于 s2 的节点"是哪几个，批注也挂不到步骤编号上。改动里每个节点带一个步骤编号；一步可以搭多个节点（s1 大概是定时触发加筛文件两个）。【已做：节点上的 `step`】
- **重做上游会让下游的线悬空。** s1 换了节点，s2 接过来的那条线一时接不上。所以闸门分两层：每份改动过一次，只查改动自己；整轮走完，整张画布过一次（线都接上、必填的格填了或标了待填）。末尾不过，把错误发回那一步的执行者，跟方案闸门打回一样是机器活。【已做一半：两层都查了，末尾查出来只写进记录，还没自动发回】
- **批注和方案打架时谁算数。** "先拆成单页"之后，方案里 s1 的出口还写着"文件清单"。批注更晚、更具体，以批注为准，方案不自动改。批注其实改了链路形状的（多一步、少一步、换目标），执行者交回 `replan_required`，转去走 Plan Agent。
- **重走每步都叫一次模型。** 十五步就是十五次，多数在说跳过。三样输入（这一步的方案文字、上游节点、批注）一样都没变的步，状态机可以不叫模型直接记跳过，make 的思路。先不做，画面小的时候不值。

### 还没定的：执行者没完成的时候交回什么

上面的画面默认每一步都做成了。没做成的几种收场，讨论中列过、还没逐条确认：

- 要问用户：问题挂在这一步，轮到用户；答了再按开始，从头重走。
- 平台没这个能力：缺什么挂在这一步，轮到用户；第一版不自动找路。
- 发现剩下的方案走不通：它的发现作为一条消息进对话记录，Plan Agent 出新方案给用户看，不自动接着执行。（现在有一半：断口卡上人按「改方案」，状态机把停在哪儿、闸门退了什么作为一条消息交给 Plan Agent——`escalate`。执行者自己还不会说。）
- 用户按停：这一步作废，画布停在上一次提交；下次按开始从 s1 重走，提交过的步"已经有了"。
- 方案换了版本（用户在主输入框又说了话、过了闸）：得重新按开始，不自动跑。

洞（2026-09-02 发现，待补）：批注挂上去永远不摘，这一版重走用过了，下次按开始它还在，执行者又重做一遍。补法：一步做完（做完或已经有了）摘这一步的批注，记进那次走步的记录；没走到的留着。

挂账：空格怎么填（在节点上直接填，还是回主输入框答 q3 出第三版方案再按开始，两条路的沉淀不一样）；平台没能力时的自动找路；用户手改节点走不走闸门；几次没过闸的往返要不要留一点给下一轮当教训。
