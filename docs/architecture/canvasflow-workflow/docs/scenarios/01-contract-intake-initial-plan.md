# 场景 01：信息不完整时的第一次 Plan 回合

> 早期预演，保留做过程留档。与现状不同的地方：`readiness` 已无 `blocked`；「每天什么时间运行」不再是问题，触发归执行侧配置；卡片式提问没有做；「解析」「抽取」按数据形态是两步，不是一步。真模型对同类描述的实际产出见 `fixtures/observed/run1-合同场景/turn-1.plan.json`。

## 场景前提

- 画布是空的，还没有工作流节点。
- Plan Agent 能看到稳定的 System Prompt、可用工具说明和输出约束。
- Plan Agent 能看到下面这一条当前用户消息。
- 可用上下文不包含历史聊天、用户长期记忆、已有工作流或资源查询结果。
- Plan Agent 此时还没有查询任何数据源、文件目录或数据表。

历史信息、用户偏好和环境信息只有被明确注入本轮上下文并标明来源时，才能作为当前事实使用。

## 当前用户输入

> 每天读取新增合同，解析内容，抽取关键字段并写入合同表。

## 当前缺失的信息

当前输入没有提供：

- 合同来源、访问位置和文件格式；
- 每天的运行时间和时区；
- “新增合同”的判定方式；
- 需要抽取的字段、类型和校验规则；
- 目标连接、数据表、字段映射和写入策略；
- 异常处理、重试和运行通知要求。

Plan Agent 将这些内容保留为待确认问题，不自行补全答案。

## Plan Agent 对外提出的计划结果

Plan Agent 不输出内部思考过程。它提出的是下面这份可被系统接收的语义结果。

### 端到端目标

建立一条每天处理新增合同的工作流：取得本轮新增合同，将内容解析成可处理的形式，抽取用户需要的结构化字段，并把结果写入指定的合同表。

### 当前完整程度

`partial`

原因不是系统无法理解用户要做什么，而是处理路线已经成立，但关键输入、字段和输出配置仍然缺失。当前可以继续形成骨架，不能声称工作流已经可运行。

### 处理步骤

#### 步骤一：取得本轮新增合同

- 目标：在每日运行时取得尚未处理的新增合同。
- 已知约束：只处理新增内容；周期为每天。
- 尚未确定：数据源、合同格式、运行时间、时区以及“新增”的判定依据。

#### 步骤二：解析合同内容

- 目标：把合同转换成后续字段抽取可以使用的内容。
- 依赖：步骤一实际取得的合同及其真实格式。
- 尚未确定：文件类型、加密或扫描件等异常情况的处理要求。

#### 步骤三：抽取结构化字段

- 目标：从解析结果中形成用户需要的合同字段。
- 依赖：步骤二的实际输出。
- 尚未确定：字段清单、字段类型、必填规则以及无法识别时的处理方式。

#### 步骤四：写入合同表

- 目标：把抽取结果持久化到用户指定的合同表。
- 依赖：步骤三形成的真实字段结构。
- 尚未确定：目标连接、数据表、字段映射、追加或更新策略以及去重依据。

这里的一个步骤只是一个处理目标，不等于一个画布节点。后续执行 Agent 可以用零个、一个或多个节点实现当前目标，也可以根据已经提交的画布判断某个目标已被前序实现覆盖。

## 用户实际看到的 Plan

右上角的 Plan 入口先展示：

> **合同信息入库** · 信息待补充

展开后，用户先看到自己的原话和 AI 对这句话的理解。

### 你的描述

> 每天读取新增合同，解析内容，抽取关键字段并写入合同表。

### AI 的理解

| 你说的 | AI 理解的 |
| --- | --- |
| 每天 | 这是一个周期性运行的工作流，但具体时间和时区未知。 |
| 读取新增合同 | 每轮只处理某个增量范围内的新合同，但“新增”的判定方式未知。 |
| 解析内容 | 合同需要先转换成后续可处理的内容，但来源和文件格式未知。 |
| 抽取关键字段 | 需要产生结构化结果，但字段清单和字段规则未知。 |
| 写入合同表 | 结果需要持久化，但目标表、字段映射和写入策略未知。 |

这部分展示的是 AI 当前形成的意图理解，不是内部推理过程。每一行都可以成为对话中的引用对象；用户纠正某一行后，Plan Agent 更新意图理解，并重新检查后面的处理计划。

### 处理计划

> 每天取得新增合同 → 解析内容 → 抽取字段 → 写入合同表

同时通过对话框给出四个可以回答或跳过的问题：

1. 合同从哪里读取？
2. 需要抽取哪些字段？
3. 结果写入哪一张表？
4. 每天什么时间运行？

每个问题都允许用户选择“稍后补充”。如果尚未查询到真实资源，卡片只能提供“选择已连接资源”这类操作入口，不能展示模型编造的 bucket 或表名。

用户展开完整 Plan 后，可以看到每一步的目标、缺失信息和“当前只能生成骨架”的说明，但仍然看不到模型的内部推理。

## 此时的画布状态

- 画布上还没有凭空出现一张完整工作流。
- Plan 已经可以在右上角被查看和纠正。
- 用户如果选择先补充信息，新的回答会回到 Plan Loop，更新同一份结构化 Plan。
- 用户如果选择先搭建骨架，状态机会把尚未解决的问题和“禁止猜测”的约束一起交给执行阶段，画布再随着每轮已校验的实际结果逐步长出来。

## 状态机此时需要接收的含义

状态机接收的不是另一份独立生成的计划，而是同一份 Plan 的运行投影：

- 用户本轮的原始描述；
- Plan Agent 对原始描述形成的意图理解；
- 当前端到端目标；
- 四个处理步骤及其依赖；
- 当前完整程度为 `partial`；
- 已确认事实与尚未解决的问题；
- 每一步禁止擅自推断的内容；
- 允许继续形成骨架，但产物不能被标记为可运行。

本场景只描述状态机需要接收的语义，不定义具体字段名、ID、版本号和状态枚举。

## 场景结束状态

本场景到第一次 Plan 提案结束，不调用执行 Agent，不搜索 WorkItem，也不生成任何节点。

Plan 发布后的执行启动策略不属于本场景范围。

## 本场景的验收条件

- 用户能并排比较自己的表达与 AI 的理解，并能定点纠正偏差。
- 系统理解、用户看到的 Plan 和状态机接收的 Plan 表达同一个目标。
- 所有事实都能追溯到当前 Query；没有依赖未声明的记忆。
- 未知信息没有在投影过程中消失，也没有变成模型的默认答案。
- `partial` 不会被误解为失败，也不会被误解为可运行。
- 画布只有在执行阶段产生真实、已校验的结果后才开始增长。
- 场景结束时尚未调用执行 Agent，画布中没有工作流节点。
