# 画布与对话融合：交互秩序改造计划

2026-09-05 · 分支 `codex/demo-execution-improvements`

这是供讨论和分步实施的计划。第一步已实现并验证：在节点内输入并立即发起完整工作流修订，在原节点得到反馈。第二、三步继续作为待讨论计划。

## 这次要得到的用户结果

用户能在发送前知道这句话针对什么，发送后在对应位置看见处理过程和结果，并随时从右上角了解整条工作流的目标、当前状态和待处理事项。

数据处理是这次交互实验的场景。Plan Agent 和执行 Agent 继续真实生成、修订画布；节点不接入真实数据处理软件包或模型来运行数据。验收针对交流、构建和修改的闭环。

已确认的方向：底部始终面对整条工作流；节点展开后提供局部输入，指令、处理状态和结果留在节点内；收起后保留简短状态，便于看全局；右上角承担 Goal 和全局状态的持续展示。

本轮讨论曾考虑“从节点入口跳到底部并带上 `@节点`”。现已调整：这种跳转让用户离开正在处理的对象，局部交流采用节点内输入。`@` 保留为以后在全局输入中引用节点的可选能力，不作为本轮局部交流的入口。

## 实施前的 gap（保留作为比较基线）

| 方面 | 当前实现 | 需要补上的能力 |
|---|---|---|
| 输入对象 | 由断口状态和方案卡是否收起决定发给谁；普通节点没有指令入口 | 底部始终面向全局，节点内输入面向该节点；输入所在的位置表达作用对象 |
| 局部指令 | 后端只存 `{ step, text }`，执行者按整步交回节点 | 保留具体节点、所属步骤、指令及其状态；执行者知道这一轮究竟要求修改哪里 |
| 交流的落点 | 全局对话集中在方案卡；节点只有配置、旁白和空位 | 局部指令、处理状态、简短结果或失败原因留在相关节点上，按需展开 |
| 全局状态 | 方案卡生成前负责问答，生成中报进度，完成后主要回看旧内容 | 持续展示目标、构建状态、待处理事项，并能从事项定位画布 |
| 修改后的事实 | 配置只改浏览器对象；方案修订和重走存在状态遗漏 | 节点、执行者和 Goal 面板读同一份会话状态；修改、失败、刷新后保持一致 |

## 第一步：建立一个完整的局部指令闭环

**可体验的结果：** 流程生成完成后，用户展开任意节点，在节点内输入指令，并在原处看见处理状态与修改结果；底部输入始终用于全局交流。

已确认的交互方向：

- 底部始终面向“整条工作流”，不因展开节点、展开 Goal 面板或出现断口而切换作用对象。
- 节点展开后提供局部输入，用户在该节点内完成表达，无需移动到底部。具体排版在实现该步前细化。
- 节点内展示局部指令、处理状态和结果；收起后保留简短状态。状态文案与可展开内容仍待细化。
- 不同位置的输入共用后端指令与会话机制，每条发送后的指令保留自己的作用对象。

支撑这段交互的实现：

- 请求显式携带作用对象，取消通过 `broke && card.isMini` 推断目标。
- 局部指令保留节点身份、所属步骤和提交时的画布版本，穿过服务端与上下文组装，不能在中途只剩一句文字。目标已被删除或替换时，提示重新选择。
- 首次构建沿用按步骤生成；节点输入使用独立的完整工作流修订操作。S3 是指令发起点，执行 Agent 读取完整计划和最新全画布，审视全部步骤，可以连带修改 S5，只提交必要的节点与连线差量。不能调用一次 `runStep(S3)`，也不能从 S1 逐步重走代替此操作。
- 差量先合入临时画布，对整图执行机器可完成的检查；检查失败原样退回本轮 Agent 修正，通过后原子提交一个新版本。每步影响说明由 Agent 给出，明确区别于机器验证；不宣称现有粗类型检查能证明字段语义正确。
- 规划、首次构建和修订共用执行权。修订保持计划内容及版本不变，失败和停止不提交半份改动。上下文带入已应用要求和有关历史摘要，保留的原始模型日志不默认全部塞回上下文。
- 记录指令待处理、已应用或失败的状态，关联本次提交结果；执行者只回复 `covered` 不能自动代表修改已应用。已应用的指令不在下一次重走时反复触发；保留它作为该步已确认要求，避免未来重建时又丢失用户的修改。
- 全局输入继续交 Plan Agent；第一版建议将需要改变整体结构的局部请求明确提示为“交给整体方案处理”，携带节点、原话和原因，沿用用户确认方案后再应用的节奏。

**验收：** 展开抽取节点，在节点内输入“金额要带币种”，最新节点上下文确实收到指令，处理状态与更新结果出现在原处；用一个包含两张卡的步骤验证目标不会退化成整步泛指令；查看其他卡片不会改变已经发送的指令归属；再重走不会重复消费这条指令，也不会忘记币种要求；无论哪个节点展开，底部消息始终进入全局对话。

本步已确认：发送后立即发起整图修订；读取全量、生成必要差量、对完整候选结果检查。用“修改 S3 导致 S5 也需要调整”的例子验收，确认一次调用任务收到全部步骤，关联改动同时提交，拒绝或停止时两处都不提交。记录真实调用耗时，后续依据测量优化。

### 第一步的实际结果（2026-09-05）

- 已实现节点内输入、状态与结果，底部输入始终进入 Plan。依据实际界面批注，节点固定标题和底部输入，中间正文按说明、参数、Prompt、数据连接、修订记录排列，只保留一个滚动区，并在滚动边缘渐隐。长 Prompt 默认展示短预览，数据连接与修订记录默认各收为一行，展开后在同一正文中阅读。底部用随文字增长的轻量输入，发送箭头内嵌，不再展示重复标题和常驻机制说明；处理过程中另写的草稿不会被完成回执清掉。
- 整图修订独立于首次走步。修订保留完整计划及画布，节点只是要求的发起点；所有步骤有影响说明，机器门禁检查完整候选后一次提交。停止、拒绝、异常和旧请求均不提交半份改动。
- 连续修订保留已应用要求和有关历史。事件流初次连接／重连提供完整快照，按序接收更新；刷新恢复当前服务内的画布和已发送记录。
- 真实五步合同链中，第一次请求修改 S3 的 amount 存储单位，同时调整了 S5，24.6 秒、1 轮，v5 → v6。第二次澄清禁止换汇，仅改 S3，31.9 秒、1 轮，v6 → v7；前次要求和 S5 修改保留。计划不变。完整记录见 [run14](../fixtures/observed/run-14-node-workflow-revision/README.md)。
- 完整自动测试 180 项通过。它们覆盖契约、整图门禁、并发与停止、上下文传递、HTTP 与事件恢复及节点交互逻辑；浏览器另检查了真实发送、反馈、草稿保留和组件窄屏布局。

后续已按用户要求补齐会话持久化与左侧管理：完整上下文和画布按会话写入本机存档，手工参数通过服务保存；全局与节点草稿留在当前浏览器。支持刷新、重启恢复及删除后的恢复，切换不影响其他会话的操作。Goal 面板仍未改造。逐步影响说明来自模型，不能当作业务语义正确的证明；这次真实生成的币种表述也确实需要一次澄清。

## 第二步：把右上角变成持续有用的 Goal 面板

**可体验的结果：** 生成完成后，用户仍可在同一位置知道目标是什么、还有什么需要处理，并直接进入相关节点。

- 常驻摘要展示当前目标、本轮构建／修改状态、待处理事项数量；展开查看已确认约束和事项明细。
- 事项来自真实会话状态：方案待确认问题、节点待配置项、失败或最终校验问题。不同种类分别计数，避免同一个问题与对应空位重复算成两项。
- 点有明确节点归属的事项，定位并展开节点；整体方案问题留在全局入口处理。
- 状态区分“本轮生成结束”和“仍有待处理项”；不把循环结束直接表达为目标已满足。
- 方案修订但尚未应用时，明确显示“方案待应用”，区分当前方案与画布已构建的版本。
- 全局方案问答保留，但进入详情；局部指令与回执由节点承担。展开 Goal 面板只影响信息展示，不改变底部输入对象。
- 配置选择先提交到会话状态再更新节点和面板；刷新与执行 Agent 的下一轮上下文读取同一值。先保证当前服务会话内一致。

**验收：** 存在两处待配置时，Goal 面板能分别定位；补完其中一处，节点、面板、刷新后的页面和下一轮 Agent 上下文一致更新。生成失败时，面板能定位原因与恢复入口。

## 第三步：保证修改后的画布仍符合当前意图

**可体验的结果：** 用户能够连续修改同一条工作流，全局与局部不会越改越脱节。

- 修订方案后，让当前步骤集合与画布对账，清理退出方案的节点和关联线。
- 更新 `covered` 判断：同时核对当前步骤要求、已确认的局部要求和输入契约；不能仅因节点存在就跳过。
- 全局修改给 Plan Agent 必要的当前画布及已确认局部要求，避免它只根据旧的全局聊天生成新方案。携带哪些信息，在该步实施前确定。
- 最终检查的问题进入节点和 Goal 的待处理事项；保留具体拒绝原因，支持带上下文转交整体方案。
- 对停止、模型错误和新建会话补齐收尾：恢复输入；已停止或已重置的请求不再覆盖当前状态。

**验收：** 全局输入“取消写库”，确认应用后写库节点消失；全局修改抽取要求后，同名节点按新要求更新；故意缺一条依赖线时能看见问题；停止或失败后能继续操作，旧结果不会晚到覆盖新状态。

## 现有 review 问题如何进入这份计划

按影响上述闭环的顺序随步骤修复，不单开一轮全量重构：

| 随哪一步处理 | 相关问题 |
|---|---|
| 第一步 | 配置／节点事件捕获旧对象；输入目标不明确；指令永久重复挂着；请求失败后输入无法恢复 |
| 第二步 | 字段保存的 `key` 遮蔽异常；配置没有回写会话；只说话的一轮清掉当前方案；最终检查没有可见出口 |
| 第三步 | 删除步骤后旧节点残留；`covered` 漏查要求与契约；跨步连线边界；具体拒绝原因丢失；停止与重置后过期结果 |

执行实录目录隔离作为辅助修复，在需要新一轮模型验证前完成，保证前后结果能可靠比较。真实数据处理运行、复杂仪表盘图表、全局输入中的 `@` 引用和并发插话不进入这轮范围。

## 验证和协作节奏

用一条合同处理链贯穿三步：首次生成 → 在抽取节点内要求加币种并看见反馈 → 配置目标表 → 查看 Goal 待处理项 → 从底部全局输入取消写库 → 制造一次失败并恢复。

逻辑校验用固定模型响应覆盖目标路由、指令生命周期、方案修订和失败收尾；浏览器里实际检查节点内输入与反馈、全局输入的稳定作用范围、定位和刷新；最终用真实生成 Agent 走这条场景，验证指令与产物对齐。节点依旧不运行数据处理。

每次只实现并验收一个步骤。本轮确认的交互方向已同步到 README 与架构文档，其余建议在确认后再同步。当前建议先做第一步，让“对着一个节点说话，它在原处回应”成立，再依据实际体验细化 Goal 面板。
