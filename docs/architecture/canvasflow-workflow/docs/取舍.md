# 取舍

主线问题只有一个：什么样的架构，能让 AI 的输出变成生长中的工作流，而不是长在对话框里的东西。
下面每一条取舍都是被这个问题的某个具体麻烦逼出来的。记下来是为了两件事：过几个月还说得清
为什么这么切；砍掉的东西不会被无意间加回来。以后每砍一刀，往这里记。

## schema 本体

以那份为准。这里放一份当前快照，方便对着下面的取舍看——留下来的每一行和没出现的每一个

## input / output 是数据形态，不是接口声明

曾经想砍掉这两个字段——把它们看成了函数签名式的接口声明，觉得设计阶段用不上。救回它们的
是两个行业事实：数仓里 ODS 到 DWD 是清洗、DWD 到 DWS 是聚合，每一层存在是因为上一层的
数据形态逼的；RAG 链路里拿到 PDF 就必须 OCR，有了长文本就必须切 chunk，有了 chunk 才能
向量化。input/output 记的是数据处于什么状态，链条是靠"上一环的输出形态逼出下一环"往前推
的，砍掉它们，步骤之间就只剩摆放顺序，没有推导关系。

由此得到分步的判据：数据形态转变一次，就是一步。替换掉了早先拍脑袋的"三到五步"。

另一个推论：起点的 input 从可选改成必填。用户手上现在有什么形态的数据是整条链的地基，
这一条判不出来，后面每一步都是猜的。

## 上下环的衔接不做程序校验

曾经想加一条规则：下一环的 input 必须字面等于上一环的 output。放弃，因为这是假检查——
两段文字相同不代表语义上接得上，不同也不代表接不上。更糟的是它会消灭这两个字段本来要逼出
的思考：模型只要把上一环的 output 抄一遍就合规了。降级成"标黄提醒"也不行，依据是假的，
提示就是噪音。语义的衔接对不对，留给三个能判语义的角色：模型自己、核对的用户、真做的执行者。

## readiness 两档，不是三档

砍掉了 blocked。理由：数据形态判不出来、链路形状定不下来的时候，模型根本不该提交方案，
只该跟用户说话。所以"没闭环"这个状态由不调用提交工具这个行为本身承载，不需要一个永远
轮不上的枚举值。留下的两档各自对应一条真实的产品路径：ready 是可以交给执行；partial 是
形状对了、参数用户自己填，跟 Dify 给骨架让用户填表单是同一条路。

ready 不打包票工作流跑得通。执行阶段本来就设计了打回重规划的回路，计划对不对最终是被
"能不能真做出来"裁决的，所以 ready 的措辞从"可以运行"降成了"可以交给执行"。

## understanding / quote / ref：透明是必要的 harness 工程

判准是质量，该下功夫，但下了功夫也保证不了全对，所以必须同时提供迭代渠道——用户能看见
AI 把话读成了什么，能精准指着说哪里错了。quote 摘用户原话不改写，reading 写读成了什么，
按用户说话的自然停顿切，不按步骤切。ref（u1、s3、q2）首先是用户指认的坐标——他能说
"u4 你读错了"而不用重述全部——其次才是界面算增量用的标识。

## 整份重出，前端算增量

模型每一轮都基于当前全部上下文提交完整的一份方案，不是上一份的补丁——用户改一句话可能
牵动整条链，补丁式修改会留下已经塌掉的步骤。界面上的"原地改还是重来"不靠模型输出增量，
靠 ref：沿用同一个编号就是原地改，换新编号就是这条重来。契约层完整、呈现层增量，两件事
不冲突，不是二选一。

## openQuestions 的边界：错了用户看不看得出来

必须问的是这一类：错了链路照样跑、画布上一切正常、问题埋在几个月后——"新增"按什么口径算、
写到哪张表、抽哪几个字段。这些只存在于用户那边，猜错是静默的，必须问。

分叉不在此列。几条路都走得通时选错一条，工作流一出来就极其显眼，用户立刻能改，所以从
"不许自行选择"降格成"可以问一句，也可以先画一条"。实现层的选择（chunk 多大、用哪个
embedding）连问题都不算，留给执行阶段。

affects 只指向步骤，不指向 understanding。曾经想放开——一个缺口有时也悬着某条理解——
放弃，因为把缺口钉到某条具体理解上，这个动作本身就是在猜用户没说的东西，跟不许替用户
补事实是同一条原则。

## 知识边界：公有放手，私有必问

公有知识（数仓分层、OCR、切 chunk、向量化这类行业通识）模型比我们懂，提示词里一个字
不教——教了反而把它锚死在举的例子上。私有知识（哪个桶哪张表、口径、内部规范）只存在于
用户那边，必须问，不许猜。但这条二分只切"要不要问用户"，切不了"要不要写进链路"，所以
另有一条规则管后者，原文如下：

> 专业知识可以用来推导处理路径，不能用来补充用户事实，也不能替用户增加目标。仅仅因为
> 一种处理很常见、有帮助或更加完善，不足以把它加入计划。

校验、去重、监控、重试属于"常见但不必需"——不做数据照样到位——所以不进链路。

## maxLength 全部撤掉

当初加长度上限的两个理由都站不住。一是界面显示空间——但截断是前端的事，schema 卡长度
只会造成整份方案被拒收再重试，代价比省下的大。二是防模型往字段里塞长篇——但分寸该由
提示词和例子教，硬上限只会逼模型把同样的内容压缩成黑话，严格模式下还可能拦腰截断。
而且那批数字本来就是拍的，不是量出来的。minLength: 1 保留，防空串。

## additionalProperties: false，代价接近零

"关死会丢信息"是虚的代价：模型不会发明字段，想说的话会塞进语义最近的现有字段；就算
放开让它发明，前端也不认识那些字段，照样丢。关死反而有诊断价值——出现多余字段说明
契约本身缺了格子，报错比静默吞掉好。何况工具的严格模式本来就强制要求这一条。

## 走工具路线，不走纯结构化输出

纯结构化输出模式下，整条模型消息就是那份 JSON，模型没有说话的地方。把提交做成一个
工具后，一条消息天然是"先说一段话，再调用工具提交方案"：说的话给人看，提交的方案给
机器收。用户接话时，他的消息在对话里紧跟着那段话，模型不需要任何标注机制就知道在回应
什么。额外的收获：信息不够时模型可以只说话不调工具——"什么时候不提交方案"这条产品
行为因此才成为可能。

## 验证器以 schema 文件为唯一来源

出过一次事故：验证器是照着 schema 手抄的硬编码，改了 schema 它一无所知，十三条测试
照样全绿——契约实际存在两份，不一致时没有任何东西报警。改成 ajv 启动时读 schema 文件
编译，手写只留 schema 表达不了的跨字段检查（编号撞车、依赖成环、指向不存在的步骤）。
验证过这条线是通的：故意往 schema 加一条必填，十三条测试挂六条；还原后全绿。性能不是
理由——编译后单次校验 2.7 微秒。

这道闸门只判形式，判不了内容——字段填的对不对它看不见。内容靠三层，一层比一层硬：
提示词管分寸，用户对着回读核对，执行者真做的时候撞上就打回。内容对不对，最终是被
"能不能真做出来"裁决的。

## 插座厂商中立，保证归闸门

要求是什么模型都能接入。行业的公共插口是 OpenAI 兼容的对话接口，几乎所有模型——
含自部署的开源模型——都说这口话，所以调用层就用裸 HTTP 打这个接口，不引任何一家的
SDK，换模型只是换地址、key、模型名三个配置。放弃的是各厂商的生成端强制（比如 Claude
的严格模式）：约束确实生效得更早，但各家支持的 schema 写法参差不齐，一依赖就锁死在
一家。于是 schema 对模型降为说明书，唯一的保证是我们自己的闸门——校不过就把错误
原样发回去让模型重交完整一份，重试有上限，超了就停下来报错，不无限打转。

## 问了再猜，猜要看得见

对照另一份独立推出来的设计时定的。它的做法是猜了就画：不知道合同放哪，就按"对象
存储"先画读取节点，下游对着这个猜画下去，几秒钟一张完整的画。好处是第一眼看见画布
之前最短，用户对着具体节点反应比对着一串问题作答容易。坏处是猜的东西往下传：猜错
一个，后面一串跟着重画，它那套影响分析和重绑有一半是在管这个。

我们原来的规矩在另一头：错了看不出来的必须问，不许用默认值填。它卡在用户答不上来
的时候——合同是别的部门给的，放哪他真不知道，再问一遍等于没问。

取中间：先问；问了还说不清，按最常见的一种先画，问题留在待确认里，提交之前说一句
按哪种画的。猜可以，但猜的必须让用户知道是猜的，否则就是换了个名字的默认值。
执行者那边到时候接上同一条：画布上猜的节点带标记、能一键改、没确认不许跑。

## 备选项由模型给，私有事实不给

问题要做成可选的卡片，就得有选项。选项从哪儿来分两种：答案的几种可能是公有知识的（扫描件还是
带文字层、"新增"按落库时间还是文件名），模型列得出来，填进 `options`；答案只存在于用户那边的
（写哪张表、抽哪几个字段），模型列不出来，不填，用户自己写，将来由平台真实查询给候选。不许模型
替私有事实编选项，跟不许它用默认值填一样是同一条原则。放弃的是"所有问题都必须带选项"——那会逼
模型给私有事实编候选。这个字段不是设计出来的，是首轮真模型在问题文本里自己塞了三个备选项逼出
来的。

## Plan 阶段的状态：回合制，方案只在过闸时换

Plan 阶段的状态就三样：对话记录、过了闸门的每一份方案（最后一份是当前方案）、这一轮跑没跑着。
规则一条：当前方案只在新的一份过了闸门时才换；只说话的一轮、被停掉的一轮、几次都没过闸的一轮，
都不碰它。并发靠回合制消掉：一轮在跑的时候不收第二句，要插话先按停，停掉的那轮当没发生，只留
用户那句。放弃的是早先设计的乐观并发——requestId、基线检查、过期丢弃——它解决的麻烦是两方同时
动，回合制让两方从不同时动，那套机器就没有出场理由。停止必须是一个明确的动作（按钮），不能从
"用户又打了字"推断：手滑打的字会把正在跑的一轮作废，还逼模型去读一句垃圾。

## 提示词只写模型眼前有的东西，规则从后果里长出来

两条尺子，2026-09-02 定。一，不写禁令，写后果：告诉模型"编号换了内容会怎样"，规则自己就
长出来了，光说"不许复用编号"它只能照办，照办的东西迁移不了。二，提示词里出现的每样东西
模型都得能在自己眼前找到——对话记录、schema、它上一轮交的那份、行业常识。它没见过界面，
拿"界面会原地变形"当理由，等于让它想象一个界面再为它优化；参数里冒出一个它不认识的键
（契约顶层的 description），它就猜那是个格子，两次被闸门打回。放弃的是"把系统的每个
下游机制都告诉模型"——告诉得越多，它猜得越多。同一条原则管闸门：闸门只拦机器缺了转不动
的东西，凡是让模型为了过闸而做特定努力的规则，都在把它的目标从"把链路想对"改成"把闸门
过掉"，那份努力就不纯粹了。闸门按这条重审，见观察。

## 批注攒着按开始重走，不批一条跑一条

执行者跑完，用户对着完整的工作流在节点上批注。批注怎么被消费，两种：批一条跑一条（Cursor 对着一段
代码按 Cmd+K 那种，执行者只动这一个节点）；批完一批按开始，状态机从 s1 重走，每步执行者看画布判断
已经有了就跳过、批了的或上游变了的重做。选后者。分高下的麻烦：批的是 s1，s1 的输出变了，s2 接的
还是老的，只动 s2 之外的东西看不见，s2 就悄悄错了。放弃的是"批一条跑一条"的即时感。

另一条一起放弃的：在提示词里写"顺便检查整体顺不顺"来兜这个麻烦。那句话要的是自觉不是眼前的东西，
模型要么翻到一半漏一个接口，要么回一句"已检查"，外面分不出来，目标函数从"把 s1 修好"变成"显得检查
过了"。重走把全局一致拆成每步看一个接口，由走法保证，不由自觉保证。类比是改了函数签名靠编译器走每个
调用点，不靠"保持一致"那句话。

## 语言：JavaScript，因为状态机和画布是同一种语言

这条 2026-09-02 才补记。9 月 1 日的基线提交里 Gate 就已经是 JavaScript，之后每一步顺着写，没人回头
记过为什么。产品决策者不读代码，这个选择只能依据解释判断，所以把理由写清楚，让它能被检验。

留下 JS 的理由，按分量排：一，最终形态是浏览器里的画布，攥着方案、画布、批注的那个会话对象可以
原样跑在浏览器里或画布旁边的 Node 服务里，换语言就是前后端两套；二，系统里流动的全是 JSON（契约、
模型交回的、画布），JS 不需要转换层；三，Node 22 自带 fetch、测试跑器、读 .env，调模型是一次普通
HTTP 请求，克隆下来只要一个 Node 就能跑。放弃的是 Python 那边他更顺手的可能；架构本身不依赖语言，
契约、提示词、实录都是 JSON 和 Markdown，代码一千行上下，真要换代价还小。

挂账：没有类型。画布和执行者交回的形状会越来越多，现在靠闸门里手写的检查守着。往后要么给画布也
写一份 JSON Schema，要么上 TypeScript。

## 平台目录不塞给模型，三层披露

执行者要对着真平台（n8n）搭节点。目录从官方镜像导出，559 种节点、全部参数说明，精简后 6.8MB。
第一版想法是把 559 个名字的索引常驻给模型，理由是"只有 70KB，撑不爆上下文"。讨论后否掉：
上下文没撑爆不代表模型能高概率编排准，549 个用不上的名字都是噪音，不做渐进式披露就太没水平了。
改成三层：常驻在提示词里的只有十来个常用节点，一行一个；模型说要找什么，搜索工具回最像的几个，
只有名字和一句话；模型点名要哪个，详情工具才给参数，分操作的节点先给操作菜单、选了操作才给那种
操作的参数（Postgres 36 个参数，插入只给 7 个）。模型像人用搜索引擎：搜、看候选、点名、拿契约、
再动手，一步里多次往返。搜索本身是查词，不是向量：词出现在名字里分最高，能做的操作次之，一句话
说明最低，整个名字被覆盖再加一笔。词不对就搜不到（database 找不到 Postgres），靠常驻行和模型换词
兜着；真不够再上向量索引，挂账。

范围一起收了：这是原型，不必每步闭环。OCR、MinerU 这类模型节点这一版不用，场景改成带文字层的
PDF，真被采纳时这些节点都是现成的。

## 执行者不往回推：只在用户那边的信息留空格，不编

2026-09-02 拿 run9 的 s1 推出来。方案没写文件从哪个目录读，设计者那边认为路径是实现细节
不问。两条路：留空格让用户在卡片上填；模型编一个像样的路径再标"猜的"。选留空。他的理由：这一步
已经递过来执行了，执行者的目标函数就是执行，卡片照样出，格子留给用户配，跟成熟产品里必填项留空
的做法一样。同一条把 s2 到 s4 也定了：key、字段清单、表名、凭证全是空格。边界：平台有默认值、
不填也能跑的（几点触发）用默认值，不算空格，否则满卡片空格用户什么都得填。

放弃的是"猜一个再标猜的"。设计者那边是这么做的（问了还说不清就按最常见的画），执行者这边不同：
设计者猜的是链路走向，用户一看链就知道对不对；执行者猜的是路径和表名，看着填满了，跑起来写错地方。

一起定的两条：平台当作什么都有，demo 不设计缺节点那条路，OCR 用目录里的 Mistral；执行者不说话，
用户的眼睛在画布上，卡片就是全部。

## 执行者的提示词：英文为主，工具的话进工具，例子教形状

讨论中有人问：Claude 的工程师会这么写吗。答一半会一半不会，于是按不会的那一半改。模型读英文更稳，
中文做副本。工具怎么用写在工具自己的说明里，提示词只留判断；常驻节点是内容不是工具说明，留在
提示词里。交回的形状由工具的格子定，不用散文：散文描述一条带出口的线有三种都对的写法，概率分在
三种上；一个例子再把格子里怎么填收成一种。顺序写明，模型一路往下写，先做的定后面的路。语气平，
文学句子多一步翻译就多一处翻错。常驻十三行手写，自动生成的界面文案有的没用。

例子的场景不躲真题。第一稿说"例子用订单场景，免得跟合同真题太像被照抄"，他反问：真题是用户拿来
的任何方案，躲开我们手里这一份，明天来个做订单的用户怎么办。对。解法不是躲，是例子边上写明它教
的是形状，抄的问题出现了再加不同场景的例子。测试上另算：拿合同方案测带合同例子的提示词分数不算数，
所以例子用订单场景，且要另拿一份订单方案测是否照抄。


## 撤掉 n8n 目录，节点自己定义

一开始想对着真平台搭：从 n8n 镜像导出 559 种节点，三层披露给执行者（见上面「平台目录不塞给模型」）。两次真跑把账算清了。run11 走完了整条链，但节点都是 n8n 的，我们一个都跑不起来，画布上的卡也画不出来（卡要知道每格是什么，n8n 的参数表几百格，哪格上卡说不清）。run12 批注要「PDF 拆成单页图片」，目录里没有，执行者搜了 11 次、12 个回合没交，用户只看到「没交」。

搜索本身也是个坑：「OCR」第一名是 Chargebee，"list files directory disk" 回了 Anthropic。修搜索是无底洞，而且搜到了也不敢用。

放弃的路：修搜索、加「做不到」的交回、把 n8n 的 559 种精简成 50 种。都在替一个我们不要的东西修补。

定下的：节点由我们定义，十一种，每张卡给用户看过、点过头。表小到整张常驻在提示词里，搜、查都撤了；挑不到正好的就挑最像的并说差在哪儿，写代码兜底。n8n 只剩借鉴：看成熟厂商有哪些节点、格子怎么分。代价：以后想真跑，里子要自己写（POC 里演的）；换成接 n8n 或别的平台时，换的是里子，卡和上下游不动。
