# 执行者

## 当前新增：完整工作流修订（2026-09-05）

执行 Agent 现在有两种任务：首次构建仍交一步，完成后从节点提出的修改则审视整张画布。后者使用 [reviser.en.md](../prompts/reviser.en.md)、[workflow-revision.schema.json](../contracts/workflow-revision.schema.json) 和 [reviser.mts](https://github.com/Bai-009/canvas-first-workflow/blob/824397ed995dc7e1293a383bf3b90d1bc1cdf63e/src/executor/reviser.mts)，只提供 `submit_revision` 工具，不新增默认的二次审查 Agent。

每轮读取完整计划和最新完整画布、发起节点、当前要求、已应用要求及相关记录。输出每一步的影响说明，只提交必要的节点与连线差量；共享门禁检查完整候选，拒绝原因反馈给同一轮 Agent 修正。保持目标及步骤职责的字段、单位等实现修改可以在这里完成；真正改变目标或步骤结构则返回 `needs_plan`，节点内说明原因，不擅自改计划。

实际 S3→S5 跨步骤修改与第二轮要求延续见 [run14](../fixtures/observed/run-14-node-workflow-revision/README.md)。以下是首次构建提示词的历史推导；早期 n8n 描述由文末“换到自己的节点表”取代。所有节点依旧只生成配置，不运行真实数据处理。

执行者拿到一步，把它在平台上做出来：选节点、填参数、连线，交回去。平台是 n8n。这份文档记的是它的提示词是怎么一条条推出来的（2026-09-02，逐条确定），以及还没做的部分。它眼前的东西是三样：提示词 [prompts/executor.en.md](../prompts/executor.en.md)、三个工具的说明（[src/executor/node-catalog.mts](https://github.com/Bai-009/canvas-first-workflow/blob/824397ed995dc7e1293a383bf3b90d1bc1cdf63e/src/executor/node-catalog.mts) 里的搜索和详情，[src/executor/submit-step-tool.mts](https://github.com/Bai-009/canvas-first-workflow/blob/824397ed995dc7e1293a383bf3b90d1bc1cdf63e/src/executor/submit-step-tool.mts) 里的交）、提示词里的一个例子。

## 用 run9 的 s1 推出来的四条

拿 run9 那份合同方案当实物，模型坐下来做 s1「筛出昨天落库的合同 PDF」，一路碰到的麻烦和当场定下的规矩：

1. **目录不知道，节点照样出，那格空着。** 方案里没写文件从哪个目录读，设计者认为路径是实现细节不问。执行者不往回推：这一步递到它手上就是要做出来的，它的目标函数是执行。所以卡片照样出，目录那格留给用户在卡片上配。参照的是成熟产品里「必填项留在卡片上」的做法，样式不学。同一条把 s2 到 s4 也定了：OCR 的 key、字段清单（q3 没答）、表名和库的凭证（q4 没答）全是空格。
2. **平台有默认值、不填也能跑的，用默认值，不算空格。** 几点触发、一批多少条。否则满卡片空格，用户什么都得填。
3. **平台当作什么都有。** 这是 demo 不是成熟产品，OCR 这类常见能力成熟产品必然具备，所以目录里缺节点那条路不设计。OCR 用目录里现成的 Mistral 节点，key 空着。「做不了」不进提示词。
4. **执行者不说话。** 「昨天落库」平台给不出落库时间，模型多半拿文件修改时间顶上，这一下从卡片上不一定看得出。三条落点：不说；每步附一句挂在卡片上；画完统一说一段。选不说：用户的注意力在长出来的画布上，卡片就是全部；这类含糊属于用户自己没表述清，他看卡片会发现。他的前提是成熟系统有记忆，这类含糊本就少；这一版没有记忆。

## 提示词怎么写的

讨论中有人问：Claude 的工程师会这么写吗。第一稿一半会一半不会，按不会的那一半改：

- **英文为主，中文副本。** 模型读英文更稳。副本等英文这版定了再写。
- **工具怎么用，写在工具自己的说明里。** 「分操作的节点先回菜单、选定操作再查一次」是 describe_node 的说明书该说的。提示词里只留判断：查了才填，没查过的参数名目录里没有，导进平台那格是空的。常驻节点是内容不是工具说明，留在提示词里。
- **交回的形状由工具的格子定，不用散文。** 契约在 [contracts/step-submission.schema.json](../contracts/step-submission.schema.json)，每格一句说明。散文描述一条带出口的线有三种都对的写法，概率分在三种上；格子把三种收成一种。
- **一个例子教形状。** 例子边上写明它教的是格式，节点该选什么来自这一步和目录。例子的场景不躲真题：真题是用户拿来的任何方案，躲开我们手里这一份没有意义。抄例子的问题若真出现，加不同场景的例子。测试上另算：拿合同方案测带合同例子的提示词分数不算数，所以例子用订单场景，且要另拿一份订单方案测是否照抄。
- **顺序写明。** 先看画布定重做还是已经有了，再定节点，再查参数，再填，再交。模型一路往下写，先做的定后面的路。
- **语气平。** 做什么、什么情况、为什么。文学句子多一步翻译就多一处翻错，而且模型学腔调，提示词像散文它就想说话，这里它该做的是调工具。
- **常驻十三行手写。** 自动生成用的是 n8n 给界面写的文案，有的没用（DeepSeek 那行是 "For advanced usage with an AI chain"）。十三行不贵，每行说它做什么、什么时候用。Mistral AI 常驻，因为搜「OCR」第一名是账单软件 Chargebee。

## 换到自己的节点表(2026-09-03)

n8n 的 559 种撤了。run12 把问题摆清楚了:批注要的能力目录里没有,执行者搜了 11 次、12 个回合没交;就算搜到了,那些节点我们也跑不起来,POC 里只会添 bug。节点由我们定义,十一种,每张卡都给用户看过、点过头(nodes/)。

执行者这边随之改的:

- 整张表常驻在提示词里(`{{node_table}}` 一行由 `renderNodeTable` 换成表),每种节点一行做什么、进出什么,每格一句怎么填。搜、查两个工具撤了,只剩交。一表喂三处:执行者照它填,闸门照它查,卡照它画。
- 提示词多了三条:挑不到正好的就挑最像的、差在哪儿写进旁白,什么都不像就写代码兜底;数据一路带着(文件读进来后一直跟着);正文和条件一律自己写完整。旁白的话改成「卡上看不出来的那一个判断」,复述格子里的值等于什么都没说。
- 闸门第二道:交回的节点对得上表——类型在表里、格子存在、要填的填了或留空或有默认值、挑一个的值在能挑的里、填个数的是数、多出口的线写了出口。跟第一道在同一个函数里。
- 来回上限 12 → 30。现在没有搜和查,一个回合就是一次交;退回的原因带着格子表的话,它该一两回合就交得上。
