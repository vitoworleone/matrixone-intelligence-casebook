# 项目化数据精炼智能体产品需求文档

## 1. 产品定位

项目化数据精炼智能体将原始多模态数据转为可复用、可追溯、可评估的数据资产。系统以文件级 Manifest 记录原子事实，以项目级 Blueprint 聚合全局洞察；用户通过对话描述目标、确认处理策略、查看质量结果，并可通过反馈推动新的处理版本。

| 层级 | 核心职责 |
|---|---|
| 文件 | Manifest 记录文件画像、处理决策、执行、质量与版本历史 |
| 项目 | Blueprint 聚合多文件特征、质量、分组、批处理策略和处理进度 |
| 对话 | 澄清业务目标、展示建议、获取用户确认和接收反馈 |
| 工作流 | 根据文件和项目画像执行解析、清洗、抽取、嵌入和导出 |

## 2. 核心价值与原则

- 将数据接入、画像、规划、执行、评估、反馈和版本化组织为一个闭环。
- 以 Manifest 为统一事实来源，所有处理决策和结果可解释、可复现、可审计。
- 以项目为批处理和洞察边界，避免将大量异构文件作为互不关联的孤岛处理。
- 优先自动路由至可靠模板；复杂或低置信场景再进入多模块规划与人工确认。
- 处理结果和原始权限关联，避免输出绕开既有访问控制。

## 3. 总体架构

![文件 Profiling、Manifest、规划智能体与反馈迭代的主流程](../assets/agent-project-planning/main-flow.png)

~~~text
原始文件 / 数据连接
        ↓
数据接入与 Profiler ─────────────→ 文件级 Manifest
        ↓                                  ↓
项目聚合与 Blueprint ←──────────────┘
        ↓
意图识别与路由 → 模板工作流 / 复杂规划 → 处理工具执行
        ↓                                      ↓
对话确认与反馈 ← 质量评估 / 数据样例 / 血缘与版本
        ↓
可供检索、分析、训练或应用使用的数据集
~~~

| 模块 | 主要输入 | 主要输出 | 职责 |
|---|---|---|---|
| 数据接入与 Profiler | 原始数据 | 初始画像 | 识别格式、结构、语言、风险和处理信号 |
| 意图识别 | 用户任务 | 目标与约束 | 澄清输出格式、范围、质量与隐私要求 |
| 路由与规划 | 意图、Manifest、Blueprint | 工作流计划 | 模板匹配、复杂规划、节点及参数建议 |
| Manifest 管理 | 全链路事件 | 文件处理记录 | 保存事实、决策、执行、质量和反馈历史 |
| Blueprint 管理 | 项目内 Manifest | 项目聚合洞察 | 文件分组、批处理策略、项目质量与建议 |
| 处理工具 | 工作流与数据 | 处理结果 | 解析、OCR、清洗、抽取、分段、嵌入、导出 |
| 质量评估 | 处理结果 | 质量报告 | 计算完整性、准确性、一致性和任务指标 |
| 反馈优化 | 用户反馈与质量结果 | 新版本策略 | 定位问题、调整流程、重跑并比较结果 |

## 4. Profiler

Profiler 是只读特征抽取能力：它不修改原始数据，输出作为客观事实写入 Manifest，供后续路由、项目分组和工作流规划使用。

### 4.1 基础画像

| 特征类别 | 内容 |
|---|---|
| 标识与规模 | 校验值、文件类型、字节数、页数、行数、字符或 Token 规模 |
| 结构 | 文本、表格、表单、幻灯片、代码、图像、音频、视频等布局信号 |
| 内容 | 主语言、领域标签、可读性、熵、重复度、关键实体线索 |
| 风险 | 潜在敏感信息、毒性或风险内容、OCR / 转写需求 |
| 项目关系 | 与项目内文件的相似度、重复族、可并行处理分组 |

### 4.2 工具要求

- 支持敏感信息扫描、语言识别、结构分析、质量评估和重复检测。
- 对扫描件、音频、视频等内容提供轻量预检，决定是否进入完整 OCR、转写或切帧处理。
- 对需要复杂解析的版面（表格、表单、幻灯片）提供布局标签，帮助选择工具与模板。
- 画像结果不可静默覆盖；重新画像应作为新记录或新版本写入。

## 5. Manifest

Manifest 是文件处理的单一事实来源，采用追加式演进。核心事实在首次画像后保持可追溯，后续模块只能追加自己的决策、结果和反馈，不能抹去既有历史。

| 区域 | 关键字段 | 写入规则 |
|---|---|---|
| 核心静态字段 | manifest ID、校验值、模态、接入时间、原始元数据、画像摘要 | 初始生成后保留 |
| 路由决策 | 模板、节点选择依据、置信度 | 追加 |
| 复杂计划 | 节点序列、参数、依赖、确认记录 | 追加 |
| 执行结果 | 输入输出摘要、耗时、状态、错误与重试 | 逐节点追加 |
| 质量评估 | 指标、抽样、异常与门槛判断 | 追加 |
| 用户反馈 | 反馈原文、影响范围、调整动作 | 追加 |
| 优化历史 | 策略变化、对比指标、适用条件 | 追加 |

Manifest 必须支持从任意输出反查源数据、处理路径、使用参数、质量依据和后续修订原因。

## 6. 项目与 Blueprint

项目是同一业务目标下文件、处理任务和版本的组织边界。Blueprint 不替代文件 Manifest，而是聚合项目范围的统计和决策。

### 6.1 项目对象

| 信息 | 说明 |
|---|---|
| 基础信息 | 项目名称、描述、创建时间、访问范围 |
| 数据摘要 | 文件数、模态分布、规模、语言、领域、敏感风险等级 |
| 质量总览 | 完整性、准确性、一致性、重复率与异常分布 |
| 文件组 | 按结构、内容或处理策略相似度形成的分组 |
| 处理建议 | 推荐模板、批处理方式、并行度与人工检查点 |
| 运行状态 | 当前任务、进度、失败项、重试情况 |
| 版本历史 | 已完成版本、质量对比、可交付输出 |

### 6.2 项目级能力

- 将相似文件分组，按组选择更一致的处理策略。
- 基于项目整体画像给出批处理、去重、分段和质量检查建议。
- 汇总文件处理状态与异常，支持从项目视图下钻到文件和节点。
- 在项目层展示版本间的输出规模、质量、失败项和策略差异。

## 7. 规划、工具与反馈

### 7.1 路由策略

1. 优先依据文件与项目画像匹配预定义处理模板。
2. 模板置信度不足或用户需求超出模板边界时，生成可审阅的复杂计划。
3. 用户确认计划后执行；用户可补充约束或要求调整计划。
4. 处理工具包括解析、OCR、敏感信息处理、字段抽取、清洗、分段、去重、嵌入、评估和导出。

复杂计划应区分可自动执行、需人工确认和不可执行三类节点；对不可执行节点给出缺少的数据、权限或工具条件，不能生成看似已完成的计划结果。

### 7.2 用户反馈

用户可通过对话指出字段遗漏、质量不足、输出结构不符或隐私处理问题。系统应：

- 将反馈关联到 Manifest 中的文件、节点和版本；
- 说明建议修改的处理策略与影响范围；
- 创建新版本并保留旧版本；
- 展示调整前后的样例、指标和异常变化；
- 对高风险操作或低置信修改请求用户确认。
- 项目级反馈只影响明确选定的文件组和新版本；不同文件组的处理策略、质量指标和版本关系须可分别查看，避免以项目汇总数字掩盖局部异常。

## 8. 数据质量、交付与验收

### 8.1 质量维度

- 完整性：是否覆盖预期文件、页、字段和数据范围。
- 准确性：抽取、识别、分类和脱敏是否满足任务定义。
- 一致性：格式、术语、字段类型和跨文件规则是否一致。
- 可用性：输出是否可被目标检索、分析或训练链路消费。
- 可追溯性：每个关键结论和数据单元能否回到来源与处理路径。

### 8.2 验收标准

- 用户可创建项目、接入数据、查看项目与文件级画像。
- 系统能为常见场景路由模板，对复杂场景展示可确认的处理计划。
- 所有任务生成 Manifest 记录，并能从结果追溯到输入与节点级执行信息。
- 项目页面能聚合质量、文件分组、进度、异常和版本差异。
- 反馈生成新版本且不覆盖历史输出；质量报告可解释通过或未通过原因。

### 8.3 限制

- 性能目标、模型选择与部署方式需按实际数据规模和运行环境验证，不应视为固定承诺。
- 多模块规划需要定义成本、超时、失败降级与人工介入策略。
- 质量评分不能替代面向具体业务的人工验收或治理审查。
