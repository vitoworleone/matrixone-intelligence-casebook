# 工作流邮件文件处理产品需求文档

## 1. 产品目标

支持对标准 MIME 邮件文件进行解析，分离元数据、正文和附件；正文复用文档解析能力，附件按文件类型独立处理，并将全部结果汇总到统一输出中。

![邮件解析流程](../assets/workflow-email-processing/email-processing-flow.png)

## 2. 范围

### 范围内

- 解析标准 MIME 格式的 EML 文件。
- 提取发件人、收件人、抄送、主题和日期等结构化元数据。
- 解析邮件正文中的文本、表格与内嵌图片；图片执行 OCR 与图像描述。
- 识别并提取第一层独立附件，交由匹配的文件解析器处理。
- 将正文、附件的图片写入同一 `images` 目录，表格写入同一 `tables` 目录。
- 将正文与附件的解析结果写入同一个解析 JSON，将分段结果写入同一个分段 JSON。

### 范围外

- 加密、受密码保护、损坏或严重不规范的邮件及附件。
- 执行邮件正文中的脚本。
- 对日历或联系人附件作专门解析；它们仅作为普通附件处理。
- 嵌套邮件的递归解析，仅处理第一层邮件与附件。

## 3. 接入与处理流程

- 支持从已接入的数据源选择 EML 文件；本期本地上传入口不支持 EML。
- 创建工作流时文档类型增加 EML。
- 邮件元数据保持为独立结构化数据。
- 邮件正文（文本、表格、内嵌图片）转为虚拟文档，使用现有文档解析器处理。
- 附件按其真实文件类型调用相应解析器。
- 按原有顺序合并元数据、正文解析结果和附件解析结果。

## 4. 解析结果

### 4.1 切换与展示

文件预览提供内容切换器，默认展示“邮件正文”，并可选择每个附件。

| 内容 | 展示方式 |
|---|---|
| 邮件正文 | 按虚拟文档的解析块展示，包括元数据、文本、图片和表格 |
| 附件 | 按相应文件类型的解析块展示 |

### 4.2 输出结构

每个解析块应包含 `type`、`level`、`source`、内容和顺序。`source` 用于区分 `email_body` 与 `email_attachment`；附件块额外记录附件文件名。

~~~json
{
  "type": "email",
  "level": "subject",
  "source": "email_body",
  "content": "邮件主题"
}
~~~

邮件元数据块使用 `type: email`，其 `level` 分别为 `sender`、`recipient`、`cc`、`date`、`subject`。正文和附件块必须保留全局阅读顺序；正文块以 `source: email_body` 标识，附件块以 `source: email_attachment` 标识并携带 `attachment_filename`。图片可分别输出 `ocr` 与 `caption` 块，表格主体使用 `table_body`。

## 5. 分段结果

- 默认展示邮件正文的分段结果。
- 邮件正文遵循文档分段展示规则。
- 附件可切换查看，并遵循各自文件类型的分段展示规则。
- 正文与附件在统一分段 JSON 内保留来源关系与文件名。

## 6. 验收要点

| 场景 | 验收标准 |
|---|---|
| 接入 | EML 可作为工作流文件类型并完成载入 |
| 元数据 | 五类核心元数据独立输出，不与正文文本混合 |
| 正文 | 文本、表格、内嵌图片按虚拟文档解析，图片可产出 OCR 与描述 |
| 附件 | 第一层所有附件被提取并按类型解析 |
| 结果 | 正文和附件可切换查看，解析与分段 JSON 可区分来源 |
| 异常范围 | 加密、嵌套、损坏等不支持场景有明确失败结果 |

## 7. 容错与结果一致性

- 单个附件无法解析时，邮件正文与其他可解析附件仍可完成；失败附件应在切换器与作业详情中显示名称、类型和失败原因。
- 邮件正文和附件的 `images/`、`tables/` 合并时必须避免同名覆盖，引用路径与最终目录保持一致。
- 邮件解析和分段切换器默认落在“邮件正文”；附件排序与原邮件中附件顺序一致。
