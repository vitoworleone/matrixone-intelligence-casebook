# MOI Knowledge Book：能力范围与设计取舍

本文记录 MOI Knowledge Book 第一阶段要解决的问题、需要通过验证确认的能力，以及刻意不纳入的方向。它是产品范围说明，不是对竞品或历史实现的逐项审计。

## 1. 核心范围

| 能力域 | 第一阶段应具备的体验 | 用户价值 |
| --- | --- | --- |
| 知识接入 | 将复杂文档、图片、表格与指定业务数据纳入明确的知识范围。 | 知道哪些资料可以被使用。 |
| 解析与分段 | 保留文档结构，并以可调整、可版本化的分段结果服务下游检索。 | 避免“上传成功但内容不可用”。 |
| 多粒度索引 | 支持文件、章节和片段三个层次的定位与召回。 | 兼顾长文理解与精确查证。 |
| 混合检索 | 结合全文与语义候选，并允许范围条件先行过滤。 | 同时处理术语、编号和自然语言提问。 |
| 证据扩展 | 为命中结果补齐相邻文本、表格行、相关图片和来源信息。 | 回答基于完整上下文，而非孤立片段。 |
| 来源治理 | 将状态、标签、版本、有效期和权限纳入可检索范围。 | 降低过期或不应访问资料进入回答的风险。 |
| 回答与引用 | Agent 使用检索证据完成回答，并提供可回看的来源。 | 用户可以自行核验关键结论。 |

## 2. 优先级取舍

MOI Knowledge Book 优先解决“企业资料是否可用、是否可信、是否可维护”，而不是堆叠检索算法名词。

| 优先做 | 原因 |
| --- | --- |
| 复杂文档解析与证据定位 | 企业价值往往首先受制于资料质量，而不是模型是否能生成更长的回答。 |
| 来源版本与有效范围 | 当内容更新或失效时，检索结果必须能同步反映变化。 |
| 引用与评测闭环 | 可验证的回答才能进入高错误成本的业务场景。 |
| 受控的 Agent 知识调用 | 让任务型体验可以使用知识，但不绕开知识范围和证据要求。 |

## 3. 需要通过验证确认的部分

以下能力是有价值的后续验证点，但不应在验证前写成既定产品承诺：

| 验证项 | 要回答的问题 |
| --- | --- |
| 重排策略 | 在特定行业资料上，二阶段重排能否显著提升前排结果质量，且值得承担延迟与成本。 |
| 图文与表格检索 | 图片、图表和复杂表格能否稳定提供比纯文本更有效的证据。 |
| 检索评测闭环 | 能否持续用代表性问题集衡量召回、引用和最终任务结果。 |
| 引用交互 | 用户是否能快速理解引用、跳回来源并发现证据不足。 |
| Agent 任务结合 | 检索证据能否在实际工作流中减少人工查找与复核时间。 |

## 4. 暂不纳入的能力

| 方向 | 暂不纳入的原因 |
| --- | --- |
| GraphRAG / 知识图谱问答 | 需要先证明实体关系和多跳问题是目标场景的主矛盾，再投入图谱构建与维护成本。 |
| RAPTOR 或摘要树检索 | 多粒度索引已能覆盖首阶段的上下文需求；递归摘要应以真实评测收益为前提。 |
| 自动查询改写与自动多跳 | 这类策略会提高不确定性、延迟和调试难度，需在基础检索稳定后再引入。 |
| 通用深度联网搜索 | 外网信息与企业受控知识是不同边界；后者优先保证来源、权限和时效。 |
| 事实核验器 | 引用与证据可追溯不等于事实自动核验；独立校验机制需结合具体风险场景设计。 |
| 行业预设分块模板大全 | 不以模板数量作为产品竞争力，先以解析质量、可配置性和评测结果判断需求。 |

## 5. 产品判断

MOI Knowledge Book 不是一个泛化的“文档聊天”入口。它的价值在于把企业资料转化为可被业务任务使用、可回看证据、可持续治理的知识基础。

对应的端到端设计见 [MOI Knowledge Book：面向复杂企业知识的可追溯检索设计](moi-knowledge-book-rag-design.md)。
