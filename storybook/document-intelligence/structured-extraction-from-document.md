## 1. 用户目标与产品承诺

**用户目标与风险。** 业务人员希望从 PDF、扫描件或图片中提取预先定义的字段，并获得可供后续系统使用的结构化 JSON；对于源文件没有提供的事实，系统不得臆造。

本 Case 控制的风险是：工作流虽然显示完成，但实际输出不符合 Schema、关键事实错误、无法追溯来源，或以看似完整的内容填补缺失事实。

**产品承诺。** 本 Case 合并验证同一条能力链的三个层次：

| 层次 | 本 Case 验证内容 |
|---|---|
| 模板入口 | 用户能够从内置工作流模板进入结构化信息提取流程，并完成必要配置。 |
| 业务流程 | 用户能够从文档输入获得可使用、可核对的结构化交付物。 |
| 底层能力 | 提取能力遵守 JSON Schema、字段类型和“无来源不臆造”的约束。 |

三层必须在同一次 Case 运行中形成闭环；仅证明算子可调用、页面可打开或工作流提交成功，都不构成通过。

**通过结论。** 仅当第 6 节所有自动可判定断言均通过、没有未说明的副作用，并且第 7 节所列证据与清理记录齐全时，本 Case 才能记为 `pass`；当前 `not run` 不代表通过。

| 名称 | 角色 | 版本与完整性 | 使用约束 |

**输入合同。** 本 Case 使用专门制作的合成工程检查记录：一份原生 PDF、一份内容等价的扫描图片、一份 JSON Schema 和一份人工核对过的标准答案。

公开 casebook 不存放输入文件本身。正式自动执行时，私有夹具仓库必须冻结文件版本与 SHA-256；Schema 至少包含记录编号、地点、测量值和条目列表，并明确字段类型、嵌套关系与必填规则。

运行前必须校验夹具版本与校验值；版本不匹配、缺少金标或夹具安全复核未通过时，结果为 `blocked`，不得以替代资料继续运行。

**本 Case 的业务路径。**

1. 将合成源文件放入 Catalog 可访问的位置。
2. 创建工作流并选择“结构化信息提取”能力。
3. 配置源文件、多模态模型、字段 Schema 和输出位置。
4. 保存并运行工作流。
5. 在执行详情中检查读取、提取与保存三个阶段。
6. 读取输出位置中的 JSON，并与标准答案逐字段核对。

## 6. 验收断言

以下断言必须逐项记录为 `pass` 或 `fail`；任何一项失败均使本 Case 失败。

| ID | 断言 |
|---|---|
| A01 | 合法 Schema 可以保存；缺少必填配置时系统给出可定位的提示。 |
| A02 | PDF 与扫描图片均能进入工作流，并获得明确终态。 |
| A03 | 输出是合法 JSON，字段名、字段类型和嵌套结构符合配置 Schema。 |
| A04 | 标准答案中明确出现的事实与输出逐项一致。 |
| A05 | 源文件未提供的事实保持空值或缺失；不得生成无来源的值。 |
| A06 | 输出可关联回本次源文件和执行记录。 |
| A07 | 执行结束后清理本 Case 创建的临时资源；清理失败必须被记录为失败或阻塞。 |

### 统一判定规则

- 输出必须能够关联本次受控输入与完整终态；缺少关联证据为 `fail`。
- 仅当私有金标、Schema、集合、计数或规则允许时，输出才可视为正确；不以模型自述或平均分替代。
- 无效、缺失、越权、超时和空结果必须具有可区分状态与原因；不得臆造内容、静默降级或把失败标为完成。
- 若本 Case 创建了临时资源，清理及回读确认是必过断言；无法清理时不得报告完整通过。

### 负向路径

对至少一种夹具定义的异常输入（例如缺失字段、非法格式、未授权范围、不可用依赖或不匹配金标）运行同一入口。系统必须拒绝、失败或产生明确的待确认状态；不得输出看似成功但不可追溯的结果。

### 人工验收边界

界面美观、长文本的主观可读性和真实客户场景适配不作为本 Case 的自动通过依据。若需要人工复核，必须单独记录结论，且不能覆盖任何自动断言失败。

## 7. 证据、报告与失败口径

**预期交付物。** 运行成功后，用户获得一个符合配置 Schema 的结构化 JSON：顶层必须包含记录标识、地点、日期、测量项列表和观察项列表；测量项必须包含名称、数值、单位和状态，观察项必须包含名称及其有来源的结论。字段值必须来自源文件；无来源字段必须为 `null` 或按 Schema 省略，不得补造内容。

**特定运行证据。**

一次 `pass` 至少需要保存以下脱敏证据：

- 夹具版本与校验结果；
- 工作流配置摘要；
- 每个阶段的终态、耗时与失败原因；
- 输出 JSON 的 Schema 校验结果；
- 字段级比对结果；
- 资源清理记录。
