# MOI Storybook 测试方法论

> 将“AI 看起来能完成任务”转化为可复现、可判定、可追溯的产品验收合同。

## 1. 定义、目标与边界

Storybook 是面向**核心用户任务**的场景化回归验收体系。一个 Storybook Case 从用户可理解的目标出发，在受控环境中准备固定输入，执行一条完整产品链路，并以明确断言与证据决定通过或失败。

它回答的问题是：**这项产品能力是否仍能把用户任务可靠地完成？** 因此，Storybook 的最小结果单位是 Case 的 `pass` 或 `fail`，不是一组模型平均分。

Storybook 不替代下列体系：

| 体系 | 主要问题 | 与 Storybook 的关系 |
|---|---|---|
| 单元/接口测试 | 单一代码单元和接口合同是否正确？ | 应先通过；Storybook 不重复覆盖所有实现细节。 |
| 集成测试 | 服务、SDK、队列、存储是否协同？ | 为 Storybook 提供可信的技术底座。 |
| Eval/Benchmark | 在同一任务集上，质量如何变化？ | 提供质量趋势和比较证据，不能覆盖掉必过 Case 的失败。 |
| 人工体验验收 | 用户是否易于理解、信任并愿意使用？ | 覆盖视觉、可用性与开放式判断；不应伪装成自动化通过。 |

Storybook 的边界也必须明确：它验证公开声明或已批准的产品合同，不把真实客户数据、生产凭据、内部地址、个人信息、原始日志或不可公开的验收材料提交到本仓库。

## 2. 设计原则

1. **从风险而非页面出发。** Case 对应用户任务和产品风险，而不是“点过了某个按钮”。
2. **一个 Case，一个可解释的主结论。** 可以跨多个服务，但应能清楚回答“它保护哪条业务承诺”。
3. **输入可重放，结论可判定。** 夹具、配置、模型/版本边界和断言必须足以复现结果。
4. **优先观察产品外部行为。** 断言用户可见结果、API 合同、结构化产物和可审计事件；不要绑定偶然的内部实现。
5. **确定性断言优先。** 对 AI 的开放式输出，应先验证终态、结构、事实、权限和副作用，再使用有版本的质量评分。
6. **失败不能被平均值稀释。** 一个 `required` Case 的 `fail`、`blocked` 或 `not run` 都是门禁信号。
7. **隔离、最小权限、必有清理。** 每次运行只拥有本次资源；外部副作用必须可控制、可验证、可逆。
8. **证据与结论分离。** 原始或脱敏后的证据记录“看到了什么”；断言记录“为何因此通过/失败”。

## 3. 从产品需求到 Case 组合

不要从“为每个功能写一个用例”开始。先把需求转成用户承诺与风险，再决定需要哪些场景。

```text
产品承诺
  → 用户任务与失败代价
  → 能力/依赖地图
  → 风险假设
  → Storybook Case 组合
  → 可执行合同、夹具、断言与证据
```

### 3.1 写出可验证的产品承诺

承诺应包含行为、条件和可观察结果。例如：

- “用户上传受支持的合同 PDF 后，可获得符合指定 Schema 的结构化字段。”
- “用户用已授权知识库提问时，回答可返回与知识来源一致的引用证据。”
- “工作流处理失败时，用户可看到失败节点和可执行的恢复信息，不能被错误标记为完成。”

“支持 PDF”“提供 AI 问答”“体验良好”都不是可直接测试的承诺，必须先具体化。

### 3.2 建立能力—风险地图

每项承诺通常依赖多个能力：数据接入、资源权限、工作流调度、模型调用、检索、Agent 工具、产物交付与清理。对每一层问四个问题：

| 问题 | 示例 |
|---|---|
| 用户会失去什么？ | 字段漏抽取、错误发送消息、看到无权数据、任务假完成。 |
| 最可能在哪里失效？ | 格式解析、异步状态、模型/工具配置、权限、输出映射。 |
| 是否可自动判定？ | ID/状态/Schema/文件/引用/副作用通常可以；视觉美感通常不可以。 |
| 失败需要怎样的证据？ | 请求 ID、执行 ID、节点状态、输出摘要、文件元数据、清理记录。 |

优先级可按 `风险 = 影响 × 发生概率 × 不易发现程度` 排序。高风险、跨域、曾发生线上事故、发布承诺或安全相关的 Case 默认进入 `required`。

### 3.3 按粒度组成测试金字塔

| 层级 | 目的 | 典型 Case | 运行频率 |
|---|---|---|---|
| S0：契约冒烟 | 验证最小入口和关键 API/SDK 合同 | 创建资源、提交任务、读取终态 | 每次提交 |
| S1：能力场景 | 验证单个产品能力的完整闭环 | 导入一份 PDF 并抽取固定字段 | 每次合并或每日 |
| S2：跨能力场景 | 验证数据、Workflow、Knowledge、Agent 的交接 | 导入 → 解析 → 建库 → 有证据问答 | 每日或候选发布 |
| S3：关键用户旅程 | 验证真实业务目标及受控副作用 | 分析附件后生成交付物并回读确认 | 候选发布/专项 |
| S4：基准与韧性 | 评估质量、容量、超时、降级与恢复 | 固定 Benchmark、限流、重试与清理 | 定期/专项 |

S3 不是越多越好；它应保留少量最高价值的“黄金路径”和关键失败路径。绝大多数细节应在更快、更稳定的 S0/S1 消化。

## 4. Case 合同：每个场景必须写清什么

Case 是文档、配置和自动执行的共同来源。它至少包含以下九部分。

1. **身份与状态**：稳定 `id`、标题、所属域、负责人、`draft/ready/deprecated`、`required/optional`、版本边界。
2. **用户任务与风险**：用户是谁、想完成什么、保护的产品承诺、失败的业务影响。
3. **范围**：覆盖能力、明确不覆盖的边界、人工验收项。
4. **夹具**：输入来源、合成/脱敏说明、版本、SHA-256、规模、许可与敏感信息确认。
5. **前置条件**：产品版本、所需模型/功能开关、账号/权限、外部依赖、配额和网络条件。
6. **执行步骤**：用户动作或 SDK/API 操作；每步描述意图和期望的可观察事件，不记录脆弱的 UI 像素坐标。
7. **验收断言**：分层定义通过条件、负向条件和允许的非确定性范围。
8. **证据与失败口径**：保存哪些脱敏字段、如何关联 request/execution/resource ID、什么情况归为产品失败、环境阻塞或用例错误。
9. **资源生命周期**：创建的资源、所有权、清理顺序、删除确认和保留策略。

### 4.1 推荐的 Case 骨架

```yaml
id: document_contract_extraction_v1
title: 从合同文档抽取关键字段并交付结构化结果
status: ready
gate: required
owners: [document-intelligence]
risk:
  promise: 支持的合同文档可产生可消费的结构化字段
  impact: high
  reasons: [release_commitment, cross_service]
scope:
  covers: [file_import, parse_v3, info_extract, result_delivery]
  excludes: [pixel_level_preview_quality]
fixture:
  kind: synthetic
  files:
    - name: contract-v1.pdf
      sha256: "<immutable-digest>"
      role: business_input
preconditions:
  required_capabilities: [catalog_import, parse_v3, info_extract]
  required_models: [text_embedding, extraction_model]
execution:
  - import_fixture
  - deploy_workflow
  - wait_for_terminal_execution
  - retrieve_output
assertions:
  terminal_status: completed
  executions: { expected_count: 1, success_ratio: 1.0 }
  output_schema: { required_fields: [contract_number, seller, buyer, amount] }
  facts:
    - field: contract_number
      equals: "MOI-2026-001"
  artifacts:
    - name: extraction.json
      min_bytes: 100
evidence: [workflow_id, execution_id, node_statuses, output_digest]
cleanup:
  owned_resources: [workflow, knowledge, catalog, imported_files]
  require_confirmed_absent: true
```

配置语法可以演进，但语义不能缺失：一个读者必须能独立理解它测什么、怎么判、为什么可信。

## 5. 夹具设计：让输入成为可控变量

AI 产品测试最常见的不可复现根源不是模型，而是输入漂移。夹具必须像代码一样管理。

### 5.1 夹具分层

| 类别 | 用途 | 要求 |
|---|---|---|
| 最小夹具 | 冒烟、单能力验证 | 尽量小，仅携带触发能力所需的信号。 |
| 代表性夹具 | 主路径回归 | 反映真实结构与难度，但已合成或脱敏。 |
| 对抗夹具 | 边界、错误处理与安全 | 空文件、重复字段、扫描件、复杂表格、越权请求等。 |
| Benchmark 夹具 | 质量对比 | 冻结选择清单、评分器版本和金标，不能混入主上下文。 |

每个文件或数据集要记录用途、来源类别、版本、完整性摘要、语言/格式/页数/行数等关键特征。标准答案、参考文件和业务输入应按角色隔离：仅业务输入进入模型上下文，金标只能进入评分和预检。

### 5.2 夹具的三条红线

- 不把真实客户资料、生产导出、秘密或个人信息作为“临时测试数据”。
- 不用会随时间变化的 URL、在线文档、第三方网页作为默认固定输入；确有需要时必须固定版本、摘要和降级策略。
- 不让同一 Case 隐式依赖其他 Case 创建的资源；每个 Case 必须能够独立运行。

## 6. 断言设计：把 AI 的不确定性拆开处理

不要用“回答里包含几个关键词”代表业务成功，也不要试图对生成文本做逐字相等。按由硬到软的层次建立断言。

| 层次 | 验证什么 | 例子 | 是否可作门禁 |
|---|---|---|
| A. 生命周期 | 是否真的执行、完成或失败 | terminal status、超时、取消结果 | 是 |
| B. 产品合同 | 接口/Schema/数量/引用是否兑现 | 字段类型、任务数、分页总数、文件 ID | 是 |
| C. 业务事实 | 关键结论是否正确 | 合同号、金额、风险项、知识来源 | 是，使用稳定事实 |
| D. 安全与副作用 | 是否遵循权限、工具和影响范围 | 无越权引用、只调用白名单工具、消息只发至受控收件人 | 是 |
| E. 质量指标 | 准确度、覆盖度、相关性、可读性 | F1、引用正确率、人工偏好 | 与阈值/趋势结合 |
| F. 体验判断 | 可理解性、视觉质量、信任感 | 页面易读、预览正确、措辞合适 | 通常人工验收 |

### 6.1 业务事实断言的写法

- 优先断言**有限且可核验的事实集合**，而不是模糊的“语义相近”。
- 对多值结果，使用集合关系、精确计数、允许缺失上限或范围，而不是顺序比较。
- 对结构化输出，先验证 Schema，再验证字段；字段缺失、类型错误或“完成但空结果”必须失败。
- 对 RAG/Agent，要求答案与引用、工具结果或受控附件之间能形成可审计链路；只看最终自然语言不够。
- 对文件交付，验证产物名、MIME、非空大小、可下载引用和必要的内容摘要；“模型声称已生成”不是证据。

### 6.2 负向断言不可省略

每个高风险 Case 至少考虑一个“绝不能发生”的结果，例如：

- 未授权知识库或附件不能进入回答引用；
- 输入文件不存在时，Workflow 不得显示 `completed`；
- 白名单之外的 Agent 工具调用必须失败；
- 外部消息不能发送到非受控收件人；
- 清理失败不得被报告为整体成功。

## 7. 执行架构：从准备到回收的可观察闭环

推荐每个 Case 使用统一的阶段模型：

```text
validate preconditions
  → create isolated resources
  → prepare and integrity-check fixtures
  → execute product journey
  → poll and collect evidence
  → assert contract
  → cleanup in reverse dependency order
  → emit a structured report
```

关键规则如下：

- **前置先于副作用。** 缺模型、权限、SDK 能力、评分器或外部服务时，在创建产品资源前失败，并记录可行动原因。
- **资源命名带 run ID。** Catalog、Database、Workflow、Knowledge、Agent、会话、临时 Channel 等都应可追溯到唯一运行。
- **轮询读全量而不是猜测。** 对异步执行按稳定分页合同获取完整记录；检查总数、重复 ID、终态和超时证据。
- **只重试瞬时错误。** 限流、短暂网络错误可有有限次数和退避；输入错误、合同违例、业务断言失败、权限拒绝不能靠重试“放行”。
- **清理按依赖逆序。** 先解绑/删除会话和 Agent，再删除 Knowledge/任务，最后回收数据源与连接器；每一步记录 `deleted`、`confirmed_absent`、`failed` 或 `blocked`。

## 8. 结果、证据与失败分类

建议将内容状态和运行状态分开：

- Case 内容状态：`draft`、`ready`、`deprecated`；
- 运行结果：`pass`、`fail`、`blocked`、`not run`。

`blocked` 只能表示已取得明确环境证据的前置无法满足，例如缺少经过验证的凭据、目标功能未部署、配额耗尽或评分器不可用；它绝不表示通过。发布规则必须明确规定 `blocked` 和 `not run` 的处置，`required` Case 默认只接受 `pass`。

每份结构化报告至少包含 Case ID/版本、运行 ID、产品/模型/配置版本、阶段起止时间、资源匿名标识、输入摘要、断言结果、失败分类、请求/执行关联 ID、脱敏诊断摘要及清理记录。证据应满足“复盘者不接触秘密也能理解结论”。

失败分类建议稳定且面向行动，例如：

- `scenario_contract_error`：Case 自身不完整或不自洽；
- `environment_precondition`：环境依赖不足；
- `tool_contract_error`：SDK/API 与预期合同不匹配；
- `product_execution_failure`：任务未成功完成；
- `product_output_contract_violation`：任务完成但输出不满足合同；
- `quality_regression`：质量门槛或基线比较失败；
- `resource_cleanup_incomplete`：资源未被可靠回收。

优先使用错误码、HTTP 状态、请求 ID 等结构化信息分类；自由文本匹配仅作为临时兼容，不应成为长期协议。

## 9. 门禁策略与运行矩阵

门禁不是“跑得越多越好”，而是以成本匹配风险。推荐建立四档：

| 触发时机 | 运行集合 | 判定 |
|---|---|---|
| Pull Request | S0 + 受影响域的快速 S1 | `required` 全部通过才可合并。 |
| 每日回归 | 全量 S1/S2 + 关键负向 Case | 跟踪稳定性、环境漂移和新增失败。 |
| 候选发布 | 全量 `required` + S3 + 关键 Benchmark | 不允许 `fail`、`blocked`、`not run`。 |
| 专项/事故后 | 对应风险簇、对抗夹具、历史回归 Case | 修复必须带回归 Case 或说明为何不适用。 |

为每个 Case 标注预计耗时、成本、外部依赖和并行安全性。超长 Benchmark 不应阻塞日常开发，但其版本与结果必须纳入发布决策。并发执行必须避免共享 workspace 配额、名称冲突和交叉读取。

## 10. AI 波动与 Flaky Case 的处理

把不稳定归因于“AI 本来就不稳定”会使 Storybook 失去意义。处理顺序应是：

1. 固定夹具、提示词模板、关键参数、模型版本或允许的模型池；
2. 区分产品终态、结构化合同、业务事实和主观质量；
3. 为可波动指标设置经过校准的阈值、置信区间或多次独立采样规则；
4. 记录每次采样的模型、参数、输入摘要和原始评分；
5. 仅对被证明为瞬时的基础设施错误重试；
6. 重复失败时将 Case 标为不稳定并停止作为静默绿灯，优先修复夹具、断言或产品问题。

不得以“重跑直到通过”“放宽关键词”“忽略 failed execution”来提高通过率。那是在降低测试覆盖，而不是提高产品质量。

## 11. Case 的生命周期与治理

### 新能力进入 Storybook 的 Definition of Done

- PRD 或设计稿中有明确的用户承诺和失败边界；
- 已完成能力—风险地图，并说明哪些风险由其他测试层覆盖；
- 至少一个 `ready` Case 覆盖主路径；高风险能力另有负向或恢复路径；
- 夹具、摘要、许可/脱敏说明和金标角色已审查；
- 断言可自动判定，人工项明确标为人工；
- 报告能关联到足够的脱敏证据；
- 资源所有权与清理行为已验证；
- Case 已指定 owner、门禁级别、预计成本和复审日期。

### 变更与废弃

- 产品承诺改变时，应修改或新增 Case，并解释与历史合同的差异；不能只改断言让结果重新变绿。
- 夹具、提示词、模型池、评分器或 Schema 的任何变化都应递增版本并保留变更原因。
- `deprecated` Case 要写明替代 Case 或失效原因，且不能直接删除历史失败证据。
- 每个季度检查覆盖盲点、长期 flaky Case、过时模型绑定和高成本低价值 Case。

## 12. 评审清单

在合并一个 Storybook Case 前，评审者应能对以下问题全部回答“是”：

- 读完标题和用户目标，能否知道它保护的业务承诺？
- 输入是否独立、公开安全、版本固定且完整性可验证？
- 前置是否可在副作用发生前检查？
- 每个通过条件是否可由产品外部证据判定？
- 是否同时验证了“完成”“结果正确”“不该发生的事没发生”“资源已清理”？
- 是否明确了无法自动化的人工验收边界？
- 失败能否被分类、定位并交给明确责任域？
- 这个 Case 的门禁级别、成本和运行频率是否与风险匹配？

## 13. 文档与目录约定

- `storybook/README.md`：体系说明、状态规则、目录导航；
- `storybook/testing-methodology.md`：本方法论和通用模板；
- `storybook/<domain>/`：按产品域组织的可公开 Case 合同；
- `storybook/<domain>/fixtures/`：仅保存小型、可公开的合成夹具或其清单；
- 私有执行配置、凭据、真实运行日志和原始证据留在受控内部系统。

每个领域目录应增加 README，说明该域的承诺、风险覆盖、Case 索引和人工验收边界。Case 文档应链接到相关 PRD、架构说明和 Eval 方法，但不引用不可公开的内部任务链接。

## 14. 起步计划

建议按以下顺序建设，而不是一次性覆盖所有功能：

1. 选出 5–10 条最高风险、最常被演示或最接近发布承诺的用户旅程；
2. 为每条旅程先写一页 Case 合同，评审用户目标、夹具和断言，而不是先写自动化代码；
3. 落地 S0/S1 的稳定、低成本 Case，建立统一报告与清理协议；
4. 逐步接入跨能力旅程、外部副作用回读与 Benchmark；
5. 用失败复盘持续补充负向路径和真实风险，而不是只增加成功演示；
6. 将 `required` 集合接入发布门禁，并定期审查其稳定性、成本和覆盖价值。

Storybook 最终不是“Case 文档库”，而是一份可执行的产品承诺清单：每个绿色结果都应意味着某个重要用户任务在明确边界内被真正验证过。
