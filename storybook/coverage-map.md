# Storybook 覆盖矩阵

本文件是 Storybook 的规划与评审索引，不是运行结果面板。它将产品承诺、主要风险和 Case 联系起来，帮助团队发现“某项能力有很多演示、但没有关键门禁”的盲点。

方法和 Case 状态定义见 [测试方法论](testing-methodology.md)。新增或废弃 `required` Case 时，必须同步更新本表。

## 1. 使用方式

1. 先登记用户可理解的产品承诺，而不是技术组件名称；
2. 为每项承诺列出最高风险和需要覆盖的路径；
3. 关联已存在的 Case；计划中的 Case 用 `planned`，不得伪装为已覆盖；
4. 标明门禁级别、执行层级和责任域；
5. 在季度复审、发布评审和事故复盘中检查空白行与过度集中区域。

覆盖状态只表示“是否已有合适的 Case 合同”，不等同于“本次版本已通过”。实际状态以运行报告为准。

## 3. 规划矩阵模板

复制下表新增条目。每个用户承诺至少要有一个主路径；高影响或安全相关承诺还必须有一个负向、权限或恢复路径。

| ID | 产品承诺 | 风险等级 | 覆盖层级 | 主路径 Case | 负向/恢复 Case | 门禁 | Owner | 状态 | 复审日期 |
|---|---|---|---|---|---|---|---|---|---|
| `<CAP-001>` | `<用户可理解的承诺>` | `<high/medium/low>` | `<S0-S4>` | `<SB-...>` | `<SB-...>` | `<required/optional>` | `<团队>` | `<planned/covered/deprecated>` | `<YYYY-MM-DD>` |

### 字段口径

- **风险等级**：按影响、发生概率和不易发现程度综合评估；`high` 默认应有 `required` Case。
- **覆盖层级**：`S0` 契约冒烟，`S1` 能力场景，`S2` 跨能力场景，`S3` 关键用户旅程，`S4` 基准/韧性。
- **状态**：`planned` 表示尚无 Case；`covered` 表示存在有效合同；`deprecated` 必须填替代 Case 或原因。
- **Owner**：维护承诺覆盖和 Case 合同的团队；不等于每次运行的执行人。

## 4. 最低覆盖标准

| 风险/场景类型 | 最低 Storybook 组合 |
|---|---|
| 高影响发布承诺 | 1 个 S1/S2 主路径 + 1 个负向/恢复路径；至少一个为 `required`。 |
| 跨服务或异步链路 | 主路径必须验证完整终态、交接 ID、输出和清理；不能只验证提交成功。 |
| 权限、数据隔离、外部副作用 | 主路径 + 明确拒绝路径；验证实际权限/收件人/工具白名单。 |
| 模型或提示词显著依赖 | 稳定事实/结构断言 + 独立 Eval 或 Benchmark；不得只用生成文本关键词。 |
| 线上事故修复 | 将触发事故的最小可公开/脱敏复现固化为回归 Case，或记录不适用原因。 |

## 5. 评审问题

- 是否存在 `required` 承诺却没有对应 Case？
- 是否只有成功路径、没有失败或越权路径？
- 是否大量 Case 集中在 UI/提交成功，却缺少异步终态、交付物和清理验证？
- 是否某个 Case 同时承担过多承诺，导致失败无法解释？
- 是否 Case 的门禁级别、成本和运行频率仍与风险匹配？

这些问题出现时，应优先调整 Case 组合或断言，而不是简单增加执行次数。
