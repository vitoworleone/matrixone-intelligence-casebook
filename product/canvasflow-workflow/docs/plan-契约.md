# PlanProposal 契约

Schema 在 [contracts/plan-proposal.schema.json](../contracts/plan-proposal.schema.json)，Gate 在 [src/plan/validate-plan-proposal.mjs](https://github.com/Bai-009/canvas-first-workflow/blob/824397ed995dc7e1293a383bf3b90d1bc1cdf63e/src/plan/validate-plan-proposal.mts)，提示词在 [prompts/plan-agent.md](../prompts/plan-agent.md)。这份文件说的是各字段为什么长这样。每一刀背后放弃了什么，在 [取舍.md](取舍.md)；真模型实际填出来的样子，在 `fixtures/observed/` 和 [观察.md](观察.md)。

角色边界见 [架构.md](架构.md)。

## 这份契约要解决什么

用户第一次说的话通常不完整。这一层不要求 Plan Agent 猜出完整工作流，而是要求它同时交出三样：

1. 当前已经能判定的处理链路：数据现在什么形态，要变成什么形态，中间经过哪几次转变；
2. 这条链路当前的可用程度；
3. 用户还必须补什么，以及缺的信息影响哪几步。

Plan 是一个可修订的处理意图，不是可执行 DSL。

它通过一个工具（`propose_plan`）提交，工具的参数就是这份 schema。模型判不出链路时不调用工具、只跟用户说话，那也是合法产出——所以契约里不需要一个「没闭环」的取值。

## 字段

### `readiness`

两档：

- `ready`：该问的都问清了，可以交给执行。
- `partial`：形状对了，但还有参数要用户自己填。

`ready` 不打包票工作流跑得通。跑不跑得通由执行裁决，执行阶段设计了退回重规划的回路。

曾经有第三档 `blocked`（连部分路线都形不成），砍掉了：那种时候模型根本不该提交方案，只该跟用户说话，「没闭环」由不调用工具这个行为本身承载。

Gate 校验它和 `openQuestions` 自洽：`ready` 不能还留着问题，`partial` 必须同时有骨架和问题。

曾经挂账：这条自洽规则让 `readiness` 完全由「有没有问题」决定，字段本身没有携带额外信息。2026-09-02 裁定：留着不动。闸门整体按「机器缺了它转不动的才拦」重审过一遍，九条检查全部保留；多出未定义字段整份拒收这条尤其要留——形状不一致，多出来的东西就没有地方接收，schema 也就失去了意义。

### `goal`

端到端意图，一句话。步骤是这个意图的展开，不是起点。

### `understanding`

对用户原话的逐段回读，一条长这样：

```json
{ "ref": "u1", "quote": "每天定时", "reading": "按固定时间触发，不是实时流式处理。" }
```

`quote` 是用户原话里的片段，原样摘出不改写，用户拿它逐句核对——不是读一段 AI 复述的话去猜哪里读歪了。`reading` 是这一段被读成了什么。

**按用户说话的自然停顿切分，不按步骤切分。** 两者条数可以不同。

用户补的话是新的原话：长出新的条目（修订轮里的 u5、u6），被它改变的旧条目原地改（u2 里「口径还需明确」的尾巴被删掉）。早期草稿里有一个平铺的 `constraints` 字符串数组，已经删掉——它没有出处，用户无从核对，界面上也没有落点。

### `steps`

数据链路。**数据形态转变一次，就是一步。**

- `title` / `intent`：这一环要达到什么结果。不写用什么工具、怎么实现。
- `input` / `output`：数据进这一环时是什么形态，出去时变成什么形态。**语义层描述，不是机器契约**——写「每份合同对应的纯文本」，不写字段名和类型。机器级的输入输出由 Execution Agent 在真实节点上确定。
- `dependsOn`：接在谁后面。

`input` 和 `output` 都必填，起点也是。第一环的 `input` 是用户手上现在有的东西，是整条链的地基，这一条判不出来，后面每一步都是猜的。链路靠「上一环的输出形态逼出下一环」往前推，砍掉这两个字段，步骤之间就只剩摆放顺序，没有推导关系。

由时间或事件触发、不接上游数据的环节，在 `input` 里说明触发来源。触发要不要单独成一步，设计层等价，不立规矩。

按这条判据，合同场景是四步：筛出新增的 PDF → PDF 变成纯文本 → 纯文本变成结构化字段 → 字段落成库里的记录。「解析」和「抽取」是两次形态转变，所以是两步。早先按「语义处理」划分时曾把它们合成一步，`fixtures/contract-processing.plan.json` 还是那一版，留着做 Gate 的测试输入；参考样子看 `fixtures/observed/`。

上下环的衔接不做程序校验：字面相同不代表接得上，不同也不代表接不上。语义衔接留给三个能判语义的角色：模型自己、核对的用户、真做的执行者。

一个 step 对应几个节点，由 Execution Agent 决定，可能是零个、一个或多个。

### `openQuestions`

用户还没说明、而这条链路需要的信息。一条长这样：

```json
{ "ref": "q2", "question": "「新增」按什么口径判断？", "reason": "决定第一环用什么标准认定一个 PDF 属于本次新增。", "affects": ["s1"] }
```

放进来的是**必须问的那类**，判据是：错了用户看不看得出来。「新增」按什么口径、写哪张表、抽哪几个字段——挑错了链路照样跑，问题埋在几个月后。这些只存在于用户那边，必须问，不许用默认值填。

分叉不在此列：几条路都走得通时选错一条，工作流一出来就显眼，用户立刻能改，所以可以问一句，也可以先画一条。实现层的选择（chunk 多大、用哪个 embedding）连问题都不算，留给执行阶段。

属于必须问的，全部列出，不替用户筛掉「不重要的」。

`reason` 写的是缺了它链路哪个部分说不清楚。`affects` 只指向步骤，不指向 `understanding`——把缺口钉到某条具体理解上，这个动作本身就是在猜用户没说的东西。

`options` 是可选的备选项。模型知道答案有哪几种可能时填上（扫描件还是带文字层；「新增」按落库时间、文件名还是合同编号），界面可以做成可选的卡片，用户可选也可写；答案只存在于用户那边、模型列不出来的（写哪张表）不填，用户自己写，以后平台能查到候选了再由平台填。这个字段是被真模型逼出来的：首轮它在 q2 的问题文本里自己塞了三个备选项，说明它想给选项但没地方放。用户在卡片上的选择最后仍拼成一句话发回模型，机制不变。

没有逐条销账。用户的回答是新的上下文，模型整份重推，问题清没清看下一份方案里它还在不在。一条里带两问无妨。

## Plan Agent 能决定什么

- 用户的整体目标；
- 对用户原话的逐段回读；
- 每一环的标题、意图、进出形态与依赖；
- 必须问的问题；
- 当前的可用程度。

## 不能决定什么

- WorkItem 名称、版本和候选；
- 节点参数、连线和画布位置；
- 用一个节点还是三个节点；
- 机器级的输入输出契约、SQL 与 Python；
- 某一步是否已被前序节点实际覆盖——那是 Execution Agent 的 `covered`；
- Plan 或 Graph 的正式版本与执行状态。

Schema 用 `additionalProperties: false` 挡住这些，测试里有两条断言守着（`workItem`、`nodeCount`）。提示词里对应的是 `<实现不归你管>` 那一节。

## `ref` 的含义

`ref` 是模型给的编号，用来表达**跨版本的同一条**。

Plan Agent 每一轮吐一整份，不吐增量。它认为这次是小修，就沿用上一版的 `ref`；认为是推翻重来，就给新的。前端拿新旧两版算 diff：`ref` 沿用的那几条原地过渡，`ref` 全新的整栏重画。模型的判断直接变成界面的动作，不需要额外加一个「这次是小修还是重写」的开关字段。

所以系统不再给每一步另发一个稳定 ID——那会产生两套编号和一张映射表，而 `ref` 已经够用。系统分配的是整份 Plan 的 `planRevision`。

`ref` 沿用不保证内容不变，只表示模型认为这还是那一条。Gate 能看见两版之间哪些 `ref` 消失了、哪些新增了，但**不拦**——模型砍掉一条理解可能是对的，界面只要知道它没了，好演退场。

这套机制在真模型上验过一轮：用户补一句之后，s1–s4 全部沿用，s2 原地改成 OCR 口径，被回答的 q1、q2 消失，q3、q4 保留原编号，u5、u6 新增。记录在 [观察.md](观察.md)。原型的演示数据就是拿这两份方案按 `ref` 差异算出来的。

## 模型输出与系统状态

步骤运行状态、节点映射、画布进度属于系统状态，不写进 `PlanProposal`。

前端渲染的是已提交的 Plan，不是模型尚未校验的原始文本。

## Gate 在这一层能校验什么

- 结构与字段类型，从 schema 文件编译——schema 是唯一来源，验证器不手抄；
- `ref` 的格式，以及唯一性（`understanding`、`steps`、`openQuestions` 各自独立）；
- 所有字符串非空；
- `dependsOn` 指向真实步骤，不自指、不成环、不重复；
- `affects` 指向真实步骤、不重复；
- `readiness` 与 `openQuestions` 自洽；
- 没有 schema 以外的字段。

没过的处理：错误写成人话，作为工具结果原样发回模型，要求重交完整的一份；连续四次没过就停下报错，不无限打转。程序一个字都不替模型改。

## 校验不了什么

- 链路的切分是不是最优的；
- 平台是不是真的存在对应能力；
- `input` 和上游 `output` 在语义上是否真的接得上——字符串对不上不代表接不上，反过来也一样。

这些只能在执行阶段依据真实能力和画布侧的校验逐步形成。Gate 只判定**能确定为假**的东西，判定不了的一律放行。内容对不对靠三层，一层比一层硬：提示词管分寸，用户对着回读核对，执行者真做的时候撞上就打回。
